# 出てしまった結果から、判断のしかたを直す

**1回ぶんを直して終わりにしない。** 直す相手は、その本文ではなく**その本文を書かせた指示**。
根拠は [docs/agent-design.md の判断の誤りを直す](../../../docs/agent-design.md#6-判断の誤りを直す)。

```
1. 何が起きたかを1つに特定する
2. 出てしまった本文を先に直す
3. どこを通ってそうなったかを辿る
4. 原因に当たるところだけ直す
5. 同じことが起きないか確かめる
6. 何をなぜ直したかを残す
```

**呼ぶ場面と呼ばない場面**

| 呼ぶ | 呼ばない |
| --- | --- |
| 同じ種類の間違いが繰り返し出ている | 買い目が外れた |
| 本人から書き方や見方の指摘を受けた | 1回だけの取りこぼしで、原因が材料不足とはっきりしている |
| 検証で止まるべきものが通り抜けた | まだ決まっていないことを決めたい（対話で決める） |

**当たったか外れたかは、判断の筋道の良し悪しではない。** 外れたことだけを理由に手順を変えない。

## 1. 何が起きたかを1つに特定する

- **同じ原因から出た症状を1つの対象としてまとめる。** どのレースの、どの馬の、どの本文かを
  特定する。原因が別なら分けるが、共通の指示が生んだ症状を機械的に別タスクや別実行へ分けない
- 本人の言葉をそのまま写す。**要約して直す対象を変えない**
- 「結論が無い」「渡した観察が消えている」「根拠が伝聞だった」のように、**何が悪かったのかを
  一文にする。** ここが曖昧なままだと、あとの経路の特定ができない

## 2. 出てしまった本文を先に直す

**指示より先に本文を直す。** 直っていない本文が残っていると、次に読む人がそれを使う。

- 書き換えは、その評価を担う役の書き方に従う（`entry_notes` は `entry-analyst`、`race_notes` は
  `race-analyst`、`horse_notes` は `horse-analyst`）
- **`author` が「人間」「対話」の行は、合意を取るまで書き換えない**
- 書いたら読み直して、入った内容を確かめる
- **ここで直した本文が、5 で使う見本になる。** どう書けば正しいのかを、実物で1つ持っておく

## 3. どこを通ってそうなったかを辿る

経路を4つに分けて、どこが原因かを見る。

| 辿る先 | 見るもの |
| --- | --- |
| 正本 | `docs/` に、その判断のしかたが書かれているか |
| 役の指示 | `agent/subagents/<役>/instructions.md` が、正本のとおりに書かせているか |
| 手順 | `agent/skills/<スキル>/SKILL.md` が、見る順序や渡すものを落としていないか |
| 検証 | `agent/subagents/verifier/instructions.md` に、それを止める観点があるか |

- **1つに決め打ちしない。** 正本にあるのに役の指示へ降りていない、役にはあるが検証が見ていない、
  のように複数にまたがることが多い
- **「AIが間違えた」で止めない。** 指示の**どの文が**そう書かせたのかまで出す。直す文が特定
  できていないなら、まだ辿れていない
- **正本に何も書かれていないなら、それは決まっていないということ。** そこで止めて本人へ返す。
  `docs/` の未確定事項を自分で確定させない（`AGENTS.md`）

## 4. 原因に当たるところだけ直す

**正本 → 役の指示 → 手順 → 検証**の順に降ろす。**役の指示だけ直して正本を放置しない。**
放置すると、次に別の役で同じことが起きる。

- **直すのは判断のしかた。今回の結論そのものを指示へ書かない。** 「この馬は強い」「この条件は
  買い」を指示に入れると、次のレースでも同じ結論が出る
- **禁止だけを増やさない。** 「〜と書かない」しか無いと、書ける内容が減って結論の無い本文に
  なる。**代わりに何を書くのか**を必ず並べる
- 役の定義は `agent/subagents/` を直し、`pnpm gen:agents` を実行する。**`.claude/agents/` は
  生成物なので直接編集しない**
- 検証で止められなかったなら、`verifier` に観点を足す。**観点は実際に起きた失敗から作る。**
  思い付きで増やすと、当てはまらない観点まで並ぶ返し方になる
- コードの変更が要るなら、そこは別のタスクへ切る（`task-management`）。開発の進め方は
  [docs/development.md](../../../docs/development.md) が正本

## 5. 同じことが起きないか確かめる

**直した宣言で終わらない。** 確かめずに閉じると、次に同じものが出る。

- 直した指示のもとで、**同じ入力からもう一度出させる。** 1 で絞った対象を使い、その役を呼び直す
- 2 で直した本文と**同じ向きの内容が返るか**を見る。文言が一致する必要は無い
- 返らないなら指示がまだ足りていない。**3 へ戻る**
- 検証の観点を足したなら、**直す前の本文を `verifier` に渡して、今度は止まるか**を見る

## 6. 何をなぜ直したかを残す

- 正本を変えたなら、`docs/` の該当箇所に**日付付きの決定として残す**
- 理由は「何が起きたか」から書く。**起きた失敗が読み取れない決定は、あとで戻せない**
- タスクとして起票してあるなら、`task-management` に従って「作業記録」を更新する

## 例（2026-09-01）

振り返りの本文が「この1回では分からない」「材料が無い」で埋まり、人間が映像で確認して渡した
内容が弱められた。辿ると、4つの経路すべてに原因があった。

| 経路 | 何が足りなかったか |
| --- | --- |
| 正本 | 本文に残す留保の基準が「競馬の言葉で書けるか」だけで、量の歯止めが無かった |
| 役の指示 | 「足りない材料を本文に残す」が独立した手順で、書くほど良い形になっていた |
| 手順 | 人間の観察を役へ渡す規則はあったが、最終的な本文と照合する手順が無かった |
| 検証 | 材料不足を突く観点はあったが、結論の有無と観察の欠落を見る観点が無かった |

**直したのは4か所すべて。** 本文だけを書き直しても、次の振り返りで同じ形が出る。

## やらないこと

- **買い目が外れたことを理由に、予想の手順を変えない**
- **未確定事項を自分で確定させない。** 決めるのは本人との対話
- **`.claude/agents/` の生成物を直接編集しない**
- **1回の指摘から、全部の役をまとめて書き直さない。** 原因に当たるところだけ直す

## 止まるところ

- 原因が「まだ決まっていないこと」だったとき
- 正本の決定そのものを変える必要が出たとき
- 人間が書いた評価（`author` が「人間」「対話」）を書き換える必要が出たとき
