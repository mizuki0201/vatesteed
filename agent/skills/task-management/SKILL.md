# タスク管理

タスクは **`docs/tasks/` 配下に1タスク1ファイル**で置く。フラットに並べ、分類は frontmatter で持つ。

`docs/tasks/` は **gitignore してある**（コミットしない）。手元だけの作業リストなので、ここに書いた
内容が他の人に共有されることは無い。**逆に、消えたら復元できない**（git 履歴に残らない）ので、
ファイルを消すときは必ず確認を取る。

ディレクトリが無ければ `mkdir -p docs/tasks` で作ってから始める。

## ファイルの形

ファイル名はタイトルを英小文字のケバブケースにしたもの（`race-name-alias-master.md` など）。
連番は付けない。

```md
---
title: レース名の別名マスタを作る
area: lib
mode: development
executor_role: dev-implementer
status: todo
created: 2026-08-09
updated: 2026-08-09
---

## なぜ

この作業が必要になった理由。会話の中で出てきたなら、そのときの経緯をここに残す。

## 依頼

本人が依頼した内容を、過去の会話を読まなくても分かるように書く。

## 完了条件

- [ ] 何ができたらこのタスクを閉じるか。チェックボックスで並べる

## 実行上の制約

- 対象外や、実行時に守る条件を書く

## 事前調査

- 確認した事実と参照元を書く。取得したページ本文は貼らない

## 現在地

- 完了した作業:
- 現在の作業:
- 次の作業:

## 問題点

- 無ければ「なし」

## 保存確認

- DB、コード差分、テストなど、このタスクの成果物を確認した結果

## 作業記録

- 2026-08-09 進捗や判断をここに追記していく

## 参照

- docs/agent-design.md — 関連する設計上の記述
```

### frontmatter

| キー | 中身 |
| --- | --- |
| `title` | 日本語のタイトル。ファイル名と対応させる |
| `area` | 責務・領域。`agent` `app` `lib` `db` `docs` `ops` など（**例示であって網羅ではない**。当てはまるものが無ければ新しく付けてよい） |
| `mode` | `development` / `racing` のどちらか。アプリ自体の開発と競馬に関する作業を混ぜない |
| `executor_role` | 実際の実行元または役。Claude Codeで開発するときは `dev-implementer`、競馬では分析する役、本人が別の実行元を明示したときはその実行元 |
| `status` | `todo` / `doing` / `blocked` / `done` のどれか |
| `created` | 起票した日 |
| `updated` | 最後に中身を触った日。**触ったら必ず更新する** |

`status: blocked` のときは、frontmatter に `blocked_by:` を足して何待ちかを1行で書く。動けるように
なったら消す。

### モード別の項目

`mode: development` では、共通項目に加えて次を置く。

- `正本となる設計`
- `実装範囲`
- `対象外`
- `変更結果`
- `テスト結果`
- `Codexの受け入れ結果`

`mode: racing` では、共通項目に加えて次を置く。

- `分析対象`
- `対象ごとの進捗`
- `DBへの保存結果`
- `参照元`
- `未登録・未分析`

開発と競馬の分析を両方含む依頼は2ファイルに分け、「参照」に依存関係を書く。`mode` を内容から
推測させない。既に完了している旧タスクには、再開しない限り新しい項目を遡って追加しない。

## 依頼別の手順

### 一覧を見せる

frontmatter だけをまとめて読む。

```bash
grep -H "^title:\|^area:\|^mode:\|^executor_role:\|^status:" docs/tasks/*.md
```

読んだら `status` ごとにまとめて口頭で伝える。ファイルの中身をそのまま貼り付けない。`done` は
聞かれたときだけ出す。領域を指定されたら `area` で絞る。

### 起票する

1. `docs/tasks/` を見て、**同じ内容のタスクが既に無いか確かめる**。近いものがあれば新しく作らず、
   そのタスクに書き足していいか確認する
2. 「なぜ」と「完了条件」を埋める。依頼の文面から埋まらない部分は推測で埋めず、本人に聞く
3. `mode` を決める。開発と競馬の分析が含まれるなら2ファイルに分ける
4. `executor_role` と `area` を決める。領域をまたぐときは主なほうを選び、もう一方は「参照」に書く
5. 共通項目とモード別の項目を埋める
6. `status: todo` で作る。すぐ着手すると分かっているときだけ `doing` にする

### 内容を更新する / ステータスを変える

**言われたときだけでなく、会話の中で状況が変わったら自分から更新する。**

- 着手した → `status: doing`
- 何かを待つことになった → `status: blocked` + `blocked_by:`
- 完了条件の一部が終わった → 該当するチェックボックスを `- [x]` にする
- 判断や方針が決まった → 「作業記録」に日付付きで1行足す
- 前提が変わって完了条件そのものが変わった → 「完了条件」を書き換え、「作業記録」に変えた理由を残す

Claude Codeが実行するときは、検索やツール呼び出しのたびではなく、意味のある作業単位が終わるたびに
「現在地」「保存確認」「作業記録」を更新する。競馬の情報を保存するときは、DBへの保存、DBの
読み直し、Markdownの更新の順に行う。再開時はMarkdownだけを信用せず、DBまたはコード差分と
照合してから続ける。

どれをやっても `updated` を実行日にする。**更新したことは必ず報告する**（黙って書き換えない）。

### 完了にする

1. 完了条件のチェックボックスが全部 `- [x]` になっているか確認する。**残っているのに閉じない**
2. DB、コード差分、テストなど、モードに応じた成果物を実行元とは別に確認する
3. Codexが受け入れた後に `status: done` とし、`updated` を実行日にする。Claude Codeは自分で
   `status: done` にしない
4. ファイルは `docs/tasks/` に置いたまま。**移動も削除もしない**

### 設計の「未確定事項」を持ち込まれたとき

`docs/` に「未確定」と書かれているものは、決めるべき問いであって作業ではない。**そのままタスクに
しない。** 「これは `docs/` 側の未確定事項なので、決めるところから始める」と伝える。決めた結果と
して手を動かす作業が出てきたら、そのときタスクに切る。

## 守ること

- **日付は実行日を使う。** 分からなければ `date +%F` で確認する。推測で書かない
- **依頼されたタスクだけを触る。** ついでに他のタスクを整えたり、気づいた作業を勝手に起票したり
  しない。起票したほうがよさそうなものを見つけたら、切っていいかを聞く
- **タスクファイルを消さない。** 不要になったものは `status` を `done` にするか、消していいかを聞く
- **コミットしない。** `docs/tasks/` は gitignore 済みなので、そもそもコミット対象に入らない
