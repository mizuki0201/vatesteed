## 更新方針

- **docs は随時更新していく。** 一度書いて固定するものではない。運用してみて違えば書き換える
- 各ファイルは **確定事項** と **未確定事項** を明確に分けて書く。未確定のものを確定として書かない
- 決まったことは該当ファイルを更新する。経緯が重要な決定は `decisions/` に記録を残す
- 列挙されたリストは、断りがない限り「例示」であって網羅ではない

## docs を正本とする変更の流れ

**エージェントや画面の挙動を変えたくなったら、実装より先に docs を直す。**

1. 人間と AI の対話で、該当するドキュメントを直す（最上流の変更なら [product.md](product.md)）
2. その差分をもとに、AI が `agent/` と `app/` の実装を直す

この順序を守るために、**同じことを docs と実装の両方に書かない**。docs は「何を・なぜ」の正本、
実装は「どうやるか」。どの docs がどの実装に対応するかは
[product.md の対応表](product.md#実装との対応)にある。

下流の作業（スキル作成など）の途中で未確定事項に当たったら、**その場で決めずに
[product.md の未決の問い](product.md#未決の問い)に1行足して止まる。**

## このプロジェクトの進め方

設計フェーズでの合意事項。エージェントもこれに従う。

- **未確定事項を勝手に確定させない。** 判断が必要になったら止まって確認する
- 挙げられた例示リストを「これが全て」と解釈しない
- ブレストでは意見を注入せず、考えを整理する役割に徹する
- 一度に複数の質問を投げない。一度に一トピックを深く扱う
- 設計フェーズでは過剰な仕様化を避け、大きな方針決定に集中する
