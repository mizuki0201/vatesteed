## 更新方針

- **docs は随時更新していく。** 一度書いて固定するものではない。運用してみて違えば書き換える
- 各ファイルは **確定事項** と **未確定事項** を明確に分けて書く。未確定のものを確定として書かない
- 決まったことは該当ファイルを更新する。経緯が重要な決定は `decisions/` に記録を残す
- 列挙されたリストは、断りがない限り「例示」であって網羅ではない

## docs を正本とする変更の流れ

**エージェントや画面の挙動を変えたくなったら、実装より先に docs を直す。**

1. 人間と AI の対話で、該当するドキュメントを直す（最上流の変更なら [product.md](product.md)）
2. その差分をもとに、AI が `agent/` と `app/` の実装を直す

この順序を守るために、**同じことを docs と実装の両方に書かない**。docs は「何を・なぜ」の正本、
実装は「どうやるか」。どの docs がどの実装に対応するかは
[product.md の対応表](product.md#実装との対応)にある。

下流の作業（スキル作成など）の途中で未確定事項に当たったら、**その場で決めずに
[development.md の未決の問い](development.md#未決の問い)へ1行足して止まる。**

**置き場は1つだけ。** 中身が運用の話でも画面の話でも、足す先はここで変わらない。以前は
product.md と2つに分けていたが、振り分けの判断そのものが迷いを生んでいたのでやめた
（2026-08-15）。

## このプロジェクトの進め方

設計フェーズでの合意事項。エージェントもこれに従う。

- **未確定事項を勝手に確定させない。** 判断が必要になったら止まって確認する
- 挙げられた例示リストを「これが全て」と解釈しない
- ブレストでは意見を注入せず、考えを整理する役割に徹する
- 一度に複数の質問を投げない。一度に一トピックを深く扱う
- 設計フェーズでは過剰な仕様化を避け、大きな方針決定に集中する
- **上流が曖昧なときは、器の話に逃げずに叩き台を先に書く。** フォーマット・仕組み・可視化の
  議論は、中身が無いままだといくら続けても進まない（下の見送った案を参照）
- **抽象論だけで返さない。** 具体のファイル・具体の例で示す

## 見送った案（docs の見せ方）

**2026-08-11 に検討して、いずれも採らなかった。** 同じ話が再燃したときに経緯を辿れるように
残す。

きっかけは「AI と人間で読みやすいフォーマットが違うので、docs と画面を対応させて、docs を
直すと画面へ自動反映される仕組みを作りたい」という相談だった。

| 案 | 採らなかった理由 |
| --- | --- |
| docs を Mermaid の図にして人間向けにする | ノードが増えると自動レイアウトが破綻する。以前 DB 設計を図にしたとき、縦に長くなって読めなくなった |
| docs の markdown を画面でそのまま表示する | レンダリングしただけの線形テキストになり、読む負担は変わらない |
| 全体像を YAML にして画面で描画する | 中身が無い段階で器を決めても空転する |

**結局、フォーマットの問題ではなく、一番上流が docs のどこにも書かれていないことが問題だった。**
中身を1枚書いたら詰まりは解けた。この経緯から、上の「上流が曖昧なときは叩き台を先に書く」を
決めている。
