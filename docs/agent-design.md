# エージェント設計

> **このドキュメントは大部分が未確定。** 引き継ぎ資料の時点で「最も手つかず」の領域。
> 下の内容を確定として扱わないこと。

## 前提（確定）

- skills は `agent/skills/` に置き、eve の `SKILL.md` 規約に従う（Agent Skills 標準と互換）
- skills はエージェント単位でスコープされる。subagent の skills はルートから見えず、逆も同じ。
  共有したい実行コードは `lib/` に置く
- `agent/instructions.md` は常時読み込み。短く安定した内容（identity と standing rule）だけに
  保ち、長い手順や状況依存の手順は skills に置く

## サブエージェントの使い分け

エージェント全体の形（オーケストレーターが人間の窓口を兼ね、必要なときだけ指示役に回る）は
[product.md](product.md#エージェントの形) が正本。ここにはその実現方法を書く。

### eve が用意している2種類

`node_modules/eve/docs/subagents.mdx` より。**継承するものが違うので、選ぶと影響が出る。**

| | ルートのコピー（組み込みの `agent` ツール） | 宣言したサブエージェント（`agent/subagents/<id>/`） |
| --- | --- | --- |
| 指示 | ルートのものを継承 | 自分の `instructions.md`。継承しない |
| ツール | ルートのものを継承 | 自分の `tools/`。継承しない |
| **スキル** | **ルートのものを継承** | **自分の `skills/`。継承しない** |
| サンドボックス | ルートと共有 | 自分のもの。継承しない |
| 役割の指定 | できない（ルートと同じ性格） | `description` で専門役を持たせる |

**宣言したサブエージェントは、ルートの持ち物を一切引き継がない。** 同じ手順を複数のサブ
エージェントに持たせたい場合、スキルの markdown をそれぞれの配下に複製するか、実行コードを
`lib/` に置いて共有する。

### どちらを使うか（2026-08-11 決定）

**専門役を宣言して立てる（`agent/subagents/<id>/`）を主体にする。**

理由は、**深い予想と高い精度を優先するから**。ルートのコピーは性格を分けられないので、
どの子も「何でも見る汎用の自分」のまま動く。役を分ければ、それぞれに専門の視点と見るべき
順序を持たせられる。

同じ役を並列で呼ぶこともできるので（18頭を「馬を読む役」で18回など）、**手分けのために
ルートのコピーを併用する必要はない**。ルートのコピーは当面使わない。

**引き受ける代償**:

- スキルの markdown を各サブエージェント配下に複製するか、実行コードを `lib/` に寄せて共有する
- 役の数だけ指示を書き分けることになる
- 分割の単位と命名規則を決める必要がある（→ 未決）

### 役の構成（2026-08-11 決定）

**工程で3層に分ける。役として立てるのは「分析する」と「検証する」の2層で、分析する役だけを
対象ごとに分ける。集めることは役ではなくスキルにする。**

| 層 | 形 | 数 | 持つもの |
| --- | --- | --- | --- |
| 集める | **スキル** | 1 | 集める手順と、収集先の制約。分析する役が必要になった時点で呼ぶ |
| 分析する | サブエージェント | 対象ごと（馬 / 血統 / 騎手 / 厩舎 / コース / 出走 / レース） | それぞれの専門の視点と見る順序 |
| 検証する | サブエージェント | 1 | 蓄積との突き合わせ。「その評価は本当か」を突く |

対象ごとに分けるのは分析だけ。集めることと検証することは対象が変わっても手順が大きく
変わらないため、1つずつにする。

**流れ**: 分析する役が情報を必要としたら、集めるスキルを呼んで自分で集める → 分析する →
オーケストレーターに返す → オーケストレーターが検証する役に渡す → 問題なければ人間に届く。

### つなぎ方

**eve では、宣言したサブエージェントが呼べるのは「自分の配下に入れ子で置いたサブエージェント」
だけ。** 横に並んだ役を直接呼ぶことはできない（`subagents.mdx`）。

#### 検証する役（2026-08-11 決定）

**オーケストレーターが橋渡しする。** 分析する役から直接渡すのではなく、分析の結果を
オーケストレーターが受け取って検証に回し、指摘があれば分析役に差し戻す。この判断は指示役の
仕事にあたる。

#### 集めること（2026-08-11 決定）

**役として立てず、スキルにする。** 各分析役が必要になった時点で呼ぶ。eve のドキュメントが
「複数のサブエージェントが同じ手順を必要とするときは、各 `skills/` に markdown を複製するか、
実行コードを `lib/` で共有する」としている形にあたる。

**手順はスキル、収集先の検査は `lib/`。** 役として分ければ「集める役だけが外部にあたる手段を
持つ」という構造で縛れるが、スキルは読ませる指示なので守るかどうかが判断に委ねられる。
**ドメインの検査を `lib/` 側に置くことで強制力を取り戻す。** これは
[compliance.md](compliance.md) の「エージェントにどう強制するか」への答えでもある。

**引き受ける代償はコンテキストの分離。** 役として分ければ集めた生の材料は集める役の中に留まり、
分析役には要約だけが返る。スキルにすると**集めたものがそのまま分析役の文脈に乗る**。
これを取り戻す手段は無い。

現状は自動収集自体を行っていない（[compliance.md](compliance.md)）ため、当面この差は小さい。
**集めた材料が分析役の文脈を圧迫し始めたら、役に切り出す。** 手順の markdown を
サブエージェントの配下へ移すだけなので、切り替えのコストは小さい。

**見送った案**（経緯として残す）:

- **孫として入れ子にする** — `オーケストレーター ⇔ 分析する役 ⇔ 集める役` の直列。
  同じ役を対象の数だけ複製することになる
- **オーケストレーターが仲介する** — 分析役が「この情報が足りない」と返して一度止まり、
  集まった情報を渡して呼び直す。往復が増える。止まった子を続きから再開する
  `experimental.subagentPersistentSessions` は**実験的機能**

**複製の実務（2026-08-16 に検証）。** 集めるスキルの markdown は分析役の数だけ並ぶ。
`.claude/skills` と同じようにシンボリックリンクで1本にまとめられるかを確かめた。
**まとめられる。ただし `skills/` ディレクトリごとにしかできない。**

| 張り方 | 結果 |
| --- | --- |
| `subagents/<id>/skills` 自体をリンクにする | **辿る。** リンク先のスキルがそのまま役に載る |
| `subagents/<id>/skills/<名前>/` をリンクにする | **辿らない。** `discover/skill-entry-not-directory` で落ちる |
| `subagents/<id>/skills/<名前>.md` をリンクにする | **辿らない。** 同じエラー |

理由は discovery の実装にある。`skills/` があるかどうかは `stat()` で見るのでリンクの先まで
辿るが、その中身は `readdir` の `withFileTypes` で取った項目を `isDirectory()` / `isFile()` で
振り分けるため、**リンクはどちらにも当たらず弾かれる。**

**確かめ方。** 使い捨ての eve プロジェクトを作り、`agent/subagents/` に4つの役を置いて、
上の3つの張り方と実体のディレクトリを1つずつ持たせた。`eve info --json` を実行し、
`.eve/discovery/agent-discovery-manifest.json` に載ったスキルと
`.eve/discovery/diagnostics.json` のエラーを見た。eve は 0.31.3。

**ここから決まること・決まらないこと。** 「1本を全役で共有する」形は作れる。一方、
**役ごとに配るスキルを変えたいなら、リンクと実体を `skills/` の中で混ぜられないので複製が要る。**
どちらを採るかは未決のまま（→ [development.md の未決の問い](development.md#未決の問い)）。

### 手順をどこに書くか（2026-08-11 決定）

**分析する役の手順は、スキルではなくその役の `instructions.md` に書く。**

eve では `instructions.md` は毎ターン読まれる恒久的な指示、スキルは必要になったときだけ
`load_skill` で読み込む任意の手順。分析する役にとって「馬を読む手順」は任意の手順ではなく
**存在理由そのもの**なので、instructions 側に置く。

したがって、素材のスキルとして枠だけ作ってあった7本（`horse-analysis` `pedigree-analysis`
`jockey-analysis` `trainer-analysis` `course-analysis` `entry-analysis` `race-analysis`）は
**各役の `instructions.md` へ移し、`agent/skills/` からは外した**。スキル名と役の名前が
似通って紛らわしくなる問題も、これで消える。

`agent/skills/` に残すのは、**オーケストレーターが使う手順**。

| 残すスキル | 立ち位置 |
| --- | --- |
| register-race / review-race | 進行役 |
| predict-race / plan-bets | 予想（分析の結果を統合するのはオーケストレーターの仕事） |
| improve-agent | 常に働く |
| write-note-article / write-zenn-article / write-x-post | 発信 |
| task-management | 開発 |

集めるスキルは**まだ作っていない**。各分析役の配下に置くことになるが、複製するか
シンボリックリンクで1本にするかが未決のため（→ 未確定事項）。

### 作った役（2026-08-11）

これは呼ばれても実行せず、未着手であることを返して止まる。

| 役 | 見るもの | 評価の行き先 | 誰が書くか |

| [pedigree-analyst](../agent/subagents/pedigree-analyst/) | 血統から適性の素地を読む | `pedigree_notes` | 役が直接 |

| [trainer-analyst](../agent/subagents/trainer-analyst/) | 厩舎の仕上げ方・ローテ | `trainer_notes` | 役が直接 |

**`horse_notes` 以外は役が直接書く（2026-08-16 決定）。** 対話で作ると宣言してあるのは
`horse_notes` だけなので（[data-model.md](data-model.md#評価が書かれるきっかけ)）、それ以外は
下の原則の「大量に発生し、機械的に決まるもの」側に寄せた。どれも1対象1行の上書きで、
`author = 'AI'` の行しか書き換えられない1文を使うため、**人間の読みを塗り潰す経路にはならない。**

**血統には材料が無い（2026-08-16 時点）。** `horses` の `sire_id` `dam_id` は全頭 null で、
役は外部サイトへアクセスしない。**pedigree-analyst は中身を書いたが、渡されない限り遡る材料が
無い**ので、当面は「材料が無い」と返して止まる。血統をどう入れるかは決めていない
（→ [development.md の未決の問い](development.md#未決の問い)）。

名前は英語のケバブケースで、**役割が分かる形**にした。eve ではディレクトリ名がそのまま
オーケストレーターから見えるツール名になり、同名のツールがあるとビルドが落ちるため、
ツール名と重ならないようにする。

評価を誰が書き込むかは下記のとおり性質で分ける。

**`horse-analyst` は書き込まない。** `horse_notes` は対話で作ると決めているため、見立てを
オーケストレーターへ返し、書くのはオーケストレーター。中身を書くときに、その役の評価が
どちら側かを必ず決める。

### 評価を誰が書き込むか（2026-08-11 決定）

**一律には決めない。評価の性質で分ける。**

| 性質 | 書き込む人 | 例 |
| --- | --- | --- |
| 大量に発生し、機械的に決まるもの | **分析する役が直接書く** | `entry_notes`（出走ごと。1レースで18行） |
| 対話で結論を出すと決めたもの | **オーケストレーター経由** | `horse_notes`（[data-model.md](data-model.md#評価が書かれるきっかけ) で「AI と人間の対話で作る」と決めている） |

**この2つ以外をどちらに寄せるかは、その都度決める。** 上の表は例示であって割り当ての一覧では
ない。**実害が出てから決めればよい**という判断で、今は原則だけ置く。

分ける理由は両取りにあたる。数の多い評価を役が直接書けば、18頭ぶんの本文がオーケストレーターの
文脈に戻らずに済む（サブエージェントに分けた利点がそこで効く）。一方、対話で決めると宣言した
ものを役が勝手に書けばその決定を破るので、そちらは必ずオーケストレーターを通す。

**気をつける点が2つ。**

- **役が直接書く経路は、検証する役を通らない。** 検証はオーケストレーターが呼ぶと決めたため。
  1対象1行の上書きなので誤りが残ることはないが、**一時的に未検証の内容が DB にある**状態は
  起きる
- **並列で書くときは範囲を重ねない。** `entry_notes` は出走ごとに行が分かれるので問題ないが、
  同じ行を複数の役から触る形にはしない

### Phase 1 で動かす（2026-08-11 決定）

Phase 1 のエンジンは Claude Code で、Claude Code が読むのは `.claude/agents/` 配下の markdown。
役の実体は eve の規約どおり `agent/subagents/` に置くので、**そこから生成して写す**。

| | |
| --- | --- |
| 正本 | `agent/subagents/<id>/`（`agent.ts` の `description` と `instructions.md` の本文） |
| 生成物 | `.claude/agents/<id>.md`（**手で編集しない**。コミットする） |
| 生成する仕組み | [lib/claude-agents/](../lib/claude-agents/)。`pnpm gen:agents` |

**シンボリックリンクではなく生成にした理由。** Claude Code の必須項目（`name` と `description`）を
frontmatter で持たせる必要があるが、eve は `instructions.md` を「書いてあるものがそのまま
プロンプト」として扱うため、frontmatter がそのまま役のプロンプトに混ざる。さらに `description` を
`agent.ts` と frontmatter の2箇所に書くことになる。生成なら**編集する場所が
`agent/subagents/` だけ**になり、ズレる余地が無くなる。

**いつ生成するか。**

- **主: 編集直後。** `.claude/settings.json` の PostToolUse フックが、`agent/subagents/` 配下への
  書き込みを検知して `pnpm gen:agents` を走らせる。Claude Code は `.claude/agents/` の変更を
  数秒で拾うので、**セッション中にズレない**
- **保険: コミット時。** `.githooks/pre-commit` が生成し直して `git add` する。VSCode で直接
  編集したときや、フックが動かなかったときの取りこぼしを拾う。**clone ごとに一度
  `git config core.hooksPath .githooks` が要る**

どちらも `mise exec` 経由で呼ぶ。フックは対話シェルではないため mise が有効になっておらず、
そのままだと Node 22 が使われて TypeScript を直接読めない。

**確かめたこと（2026-08-11）。** `.claude/agents/` は再帰的に読まれ、ディレクトリの
シンボリックリンクも辿る。frontmatter 内の YAML コメントを置いても読み込みは壊れない。
生成した8つの役が Claude Code から見えることを確認済み。

**Phase 1 と Phase 3 で違うところ。** Claude Code のスキルはセッション共通で、eve のように
サブエージェント配下に閉じない。**「集めるスキルは分析役だけが持つ」という隔離は Phase 1 では
成立しない。** ドメインの検査を `lib/` に置く決定（上記）がこれを補っている。

### 分析する役が Phase 1 で DB を読み書きする手段（2026-08-15 決定）

役の `instructions.md` には「`entry_notes` に書く」と書いてあるが、**書く手段が無かった。**
`lib/db` の `getSql()` を呼ぶコードがどこからも生えておらず、`agent/tools/` も空のため、
SQL を投げる入口が1つも無い状態だった。3つ決めて塞ぐ。

#### 入口は `pnpm db:query` の1本だけ

[lib/db/query.ts](../lib/db/query.ts) を `db:migrate` と同じ流儀で叩く。SQL は引数か
`--file`（長い日本語本文や引用符でシェルに壊されるのを避けるため）、値は `--params` に
JSON 配列で渡してプレースホルダに入れる。結果は JSON で返す。

**目的別の関数は作らない。** 2026-08-09 の決定（「最初の1レースは生SQLで登録する。関数に
何が要るかは1レース登録してみないと分からない」）をそのまま延長したもの。汎用の入口を1本
置くだけなら、`lib/` の切り方（→ 未確定事項）を先に決めてしまわずに済む。この入口は役が
読み書きするためだけのものではなく、**最初の1レースを手で登録するときにも同じものを使う**。

#### `*_notes` への書き込みは、決まった1文で行う

評価は履歴を持たない1対象1行の上書きなので、**人間が書いた行を AI が塗り潰すと戻せない**
（[data-model.md](data-model.md#ナレッジの型)）。そこで、書くときはこの1文を使う。無ければ
入れ、あれば書き換える形（upsert）に、上書きしてよい相手かどうかの条件を足したもの。

```sql
INSERT INTO entry_notes (entry_id, body, author) VALUES ($1, $2, 'AI')
ON CONFLICT (entry_id) DO UPDATE SET body = EXCLUDED.body, author = 'AI'
WHERE entry_notes.author = 'AI'
RETURNING id;
```

既存の行の `author` が「人間」「対話」なら、この文は**何もせず0行を返す**。役は書けなかった
ことを機械的に受け取れるので、[product.md](product.md#人間の読みは勝手に上書きしない) の
「合意が取れるまでその行は書き換えない」がそのまま成立する。返す先はオーケストレーター。

**ただし、この1文を使うことを仕組みで強制してはいない。** 入口は任意の SQL を通すので、
裸の `UPDATE` を投げれば人間の行も上書きできる。守られるかどうかは指示に委ねている。
強制したいと思うようになったら、`*_notes` への書き込みを `lib/` の関数に閉じ込め、入口の側で
生の `UPDATE` を弾く形にする。**今そこまでやらないのは、まだ1レースも登録していない段階で
関数の形を決めたくないため**（上と同じ理由）。この1文を `lib/` へ持ち上げることが、
**1レース登録したあとの最初の切り出し候補**にあたる。

#### 入口はスキーマを変える文を通さない

`CREATE` `ALTER` `DROP` `TRUNCATE` など**テーブルの形を変える文は、入口の側で弾く**。

手元の `.env.local` は本番の DB を指していて（[architecture.md](architecture.md#環境変数の接続先)）、
この入口は人間の確認を挟まずに動く役へ配られる。スキーマを変える経路は
[decisions/0004](decisions/0004-migrations-without-orm.md) で `db/migrations/` と
`pnpm db:migrate` に決めてあり、**検証ブランチを通してから本番へ流す**手順が付いている。
ここを迂回できると、その手順ごと無かったことになる。

**データを消したり書き換えたりする文（`DELETE` `UPDATE`）は通す。** 最初の1レースを手で
登録し直すような作業に要るため。**ここは弾いていないので、消す操作の重さは変わらない。**

#### 手段は生成のときに後付けする

**役の `instructions.md` には書かない。** eve では `instructions.md` に書いたものがそのまま
役のプロンプトになるため、`pnpm db:query` のような **Phase 1 限りの手段が Phase 3 まで
残ってしまう**。

代わりに、Claude Code へのブリッジ側（[lib/claude-agents/](../lib/claude-agents/)）に共通の
1枚を置き、生成のときに本文の末尾へ足す。Phase 3 ではこのブリッジごと捨てれば後始末が終わる。

| | |
| --- | --- |
| 足す中身 | `pnpm db:query` の使い方 / スキーマは `db/schema.sql` を読むこと / 評価は上の1文で書くこと / 0行だったときにどうするか |
| 足す相手 | 分析する役と検証する役。**`dev-` で始まる開発の役には足さない**（DB を触らないため） |

**共通の1枚なので、書いてよい相手の線引きも一緒に配る。** 役が直接書いてよいのは自分の担当の
評価だけで、対話で決めると宣言したもの（`horse_notes`）は書かずにオーケストレーターへ返す
（→ [評価を誰が書き込むか](#評価を誰が書き込むか2026-08-11-決定)）。手段だけを配ると、
中身が書かれた役から順にこの決定を破れてしまう。

**オーケストレーター自身の経路は、これでは塞がらない。** 足すのは役の生成物だけで、
`agent/instructions.md` には届かない。`horse_notes` や予想のテーブルを書くのは
オーケストレーターなので、**そちらの手段と守り方は別に決める必要がある**。
[development.md の未決の問い](development.md#未決の問い)の「オーケストレーターの
`instructions.md` に何を置くか」に含まれる話として、ここでは決めない。

#### 呼び出すときに渡すもの

オーケストレーターは **どの対象か（どの出走・どのレース・どの馬か）と、人間から出た観察・
コメントだけ**を渡す。DB から読める内容を貼り付けない。役が自分で引く。子はルートの会話履歴を
見ないので渡す文脈は選ぶ必要があるが、DB にあるものは役自身が取れるため、**18頭ぶんの本文が
オーケストレーターの文脈に戻らない**という分割の利点をここで失わない。

### 決める前に押さえておくこと

- **並列で動かすときは、書き込む範囲を重ねない。** eve のドキュメントに明記がある。
  18頭ぶんの `entry_notes` のように行が分かれていれば問題ないが、同じ行を複数から触る形にしない
- **子はルートの会話履歴を見ない。** 渡したい文脈は呼び出し時のメッセージに全部載せる
- **人間への確認は子からでも上がってくる。** `input.requested` がルートまで中継されるので、
  仕組みの上では子も人間に聞ける。ただし**窓口をオーケストレーターに集約する**方針は
  [product.md](product.md#エージェントの形) で決めているため、そこは方針で縛る
- **スキルで足りるならスキルにする。** eve のドキュメントも「別の性格・別のツール範囲・
  別のコンテキストが要るときだけ分ける」としている
- **Phase 1 は Claude Code。** サブエージェントの定義場所が eve と異なるため、
  `.claude/skills` と同じようなブリッジが要る。**張り方は未決**

## 予想の手順（2026-08-15 決定）

**1レースを予想し切るまでの手順の正本。** [product.md の運用2](product.md#2-レースを予想する1の特殊な形)
が「何をするか」で、ここが「どの順でやるか」。2026年札幌記念を手で1本通したときに詰まった
ところから決めた。

### 順序を逆にしない

**各馬を読み終わるまで、展開を組み始めない。**

```
1. レースを登録する（枠順・出走メンバー）
2. 出走馬を1頭ずつ読む      ← ここが終わるまで 3 に進まない
3. 展開を組む
4. 印を付ける
5. 買い目を組む
```

最初に手で通したときは 2 を飛ばして展開から入り、各馬の評価が後追いになった。**展開は各馬の
脚質・仕上がり・ローテーションの積み上げから出てくるもの**で、先に展開を決めるとその展開に
合う馬を後から探すことになる。

### 2. 出走馬を1頭ずつ読む

**1頭につき、次の2つを必ず両方やる。**

| | 何を |
| --- | --- |
| DB を引く | その馬の過去の出走とその評価、血統・騎手・厩舎・コースの評価 |
| 検索する | **前走から今日までの期間に起きたこと。** 調整過程、追い切り、陣営のコメント、乗り替わりの経緯、放牧や輸送 |

**検索の側は、DB が育つまでは丁寧にやる。** 蓄積がゼロに近いうちは、ほとんどの材料が外にしか
無い。DB が厚くなるにつれて検索は減っていくので、**今の手間の多さを理由に手順を簡略化しない**。

読んだ結果は `entry_notes` ほかの評価に残す。分析する役の分担は
[product.md の対応表](product.md#分析する役agentsubagents)。

#### このレースが「叩き」かどうかを見る

**「叩き」とは、そのレースを本番と位置づけず、次の目標に向けた調整として使うこと。** 仕上げを
100%にせず、走らせること自体を次への上積みにする。これがあると、能力どおりの走りをしない。

- **陣営が明確にコメントしているなら、それに従う。** 「次を見据えて」「まだ余裕を持たせて」
  「ここを使って本番へ」のような言い方が出ていれば、それが一番確かな材料
- **コメントが無いときは、陣営の立場に立って先のローテーションを組み立てる。** この馬の
  目標はどこか、そこから逆算して今回はどういう位置づけか。秋の大目標があるなら、夏のこの
  レースは仕上げ切らない可能性が高い
- **分からないなら分からないと書く。** 推測で「叩き」と決めつけると、能力を不当に割り引く

### 3. 展開を組む

**文章だけで終わらせず、レースの各時点の隊列を出す。**

| 時点 | 何を書くか |
| --- | --- |
| スタート直後 | 誰が押して出るか、誰が控えるか。枠順の影響 |
| 道中（**1〜3箇所**） | どこで隊列が動くか。ペースが緩む・締まる地点 |
| 最後の直線 | 直線を向いた時点で誰がどこにいるか |

**道中の箇所数は距離とコースで変える。**

| 距離のめやす | 道中 |
| --- | --- |
| 短距離（1400m 以下） | 1箇所 |
| マイル〜中距離（1600〜2200m 前後） | 2箇所 |
| 長距離（2400m 以上） | 3箇所 |

**これは目安であって、この3段に当てはめるための表ではない。** コーナーの数、坂の位置、内外の
回り、直線の長さで動くところは変わる。ペースが動く地点が2つしか無い2400mなら2箇所でよいし、
向正面で動く馬がいる2000mなら3箇所書く。**距離だけで機械的に決めない。**

ここまで出すと、「誰が前にいるか」ではなく**「どの地点で誰と誰が並ぶか」**まで踏み込める。
不利の受けやすさ、動くタイミング、包まれるリスクが具体的に見えるようになる。

書き込む先は `race_predictions.body`。

### 5. 買い目を組む

**1レースあたりの予算は 2,000円。** これは恒久の設定で、レースの格や自信度で変えない。

- 予算を固定するのは、**回収率を比べられるようにするため**。自信のあるレースで増やすと、
  当たったときだけ張っていたのか、見立てが良かったのかを分けられなくなる
- 券種と点数は自由。2,000円をどう割るかは予想の中身から決める
- 点数と金額は **`lib/bets` の `expandBet` で出した値だけを入れる**。手で数えない
  （[data-model.md](data-model.md#購入)）

## 振り返りの手順（2026-08-16 決定）

**レースが終わってから、評価を更新し切るまでの手順の正本。**
[product.md の運用3](product.md#3-振り返るレース後)が「何をするか」で、ここが「どの順で
やるか」。スキルの実体は [review-race](../agent/skills/review-race/)。

### 予想と順序が逆になる

```
1. 結果を取り込む（着順・人気・オッズ・時計・通過順・馬場・天気）
2. レースを評価する          ← race-analyst
3. 出走を1つずつ読み直す      ← entry-analyst
4. 馬の評価を更新する         ← horse-analyst の見立てを受けて対話で決める
5. 予想と買い目の答え合わせをする
6. 判断の誤りを直す
```

**予想では出走から馬へ積み上げたが、振り返りではレース全体から降ろす。** ペースがどうだったか、
馬場がどちらに傾いていたか、レースそのものがどの程度の内容だったかが分からないまま1つの出走を
読むと、**着順を説明するだけの話になる**。予想の時点ではそのレースがまだ走られていないので
積み上げるしかなかったが、終わったあとは上から降ろせる。

**1が終わるまで2へ進まない。** 通過順と上がり3Fが入っていない状態でレースを評価しても、
記憶と印象で書くことになる。

### 1. 結果を取り込む

`entries` のレース後の列（`finish_position` `popularity` `win_odds` `finish_time_ms`
`last_3f_ms` `corner_positions`）と、`races` の `weather` `track_condition` を埋める。

- **走らなかった馬は `status` を直す**（取消・除外・中止・失格）。着順が入るのは `出走` の
  ときだけで、CHECK 制約が効いている。人気とオッズには同じ縛りが無いので、中止・失格でも入れる
- **降着があれば `finish_position` は降着後の確定着順**（[data-model.md](data-model.md#entries)）
- 裏取りの基準は予想のときと同じ。**2回試して確からしい値が取れなければ、取れなかったと残す**

### 5. 予想と買い目の答え合わせ

**当たったかどうかではなく、どこで筋道が外れたかを見る。** 印は結論なので、印の当否だけを
数えても次に効かない。

- 予想の展開（`race_predictions.body`）と実際の隊列を突き合わせる。**各時点の隊列まで出して
  あるので、どの地点から違ったかが分かる**（→ [予想の手順](#3-展開を組む)）
- 的中と払戻は `ai_bets` の `payout` `refund` に入れる。**的中の判定と回収率は
  [lib/bets](../lib/bets/) で出す。手で数えない**（[data-model.md](data-model.md#的中の判定)）
- **買っていない馬券が当たっていたことを、外れの理由にしない。** 見るのは組み立ての筋道

### 6. 判断の誤りを直す

**残す先が2つある。何についての誤りかで決まる**（[product.md](product.md#学んで残す)）。

| 気づいたこと | 残す先 |
| --- | --- |
| その馬・そのコース・その騎手の見方が変わった | 各 `*_notes` |
| 見るべきものを見落としていた、順序が違った | `docs/` と `agent/skills/` |

後者を直すのは `improve-agent` の担当だが、**このスキルはまだ中身が無い。** 書かれるまでは、
振り返りの中で気づいたことを挙げるところまでをこの手順で行い、直すかどうかはオーケストレーター
が対話で決める。

### 止まるところ

- **`author` が「人間」「対話」の評価は、単独で書き換えない。** 前の見方・新しい見方・何がどう
  変わるのかを並べて合意を取る（[product.md](product.md#人間の読みは勝手に上書きしない)）
- **結果が出たことを理由に、予想時点の評価をさかのぼって直さない。** 予想は枠順確定直後に
  出したもので、回収率もそれで測ると決めてある（[data-model.md](data-model.md#予想と回収率)）

## 情報の集め方（2026-08-15 決定）

### 過去の出走をどこまで登録するか

**予想の対象レースは全頭を登録する。過去のレースは、読むと決めた出走だけを登録する。**

過去のレースの全頭を毎回入れると、1レースの予想でレースが数十本・馬が百頭単位になって回らない。
一方で入れないと、相手関係が DB に残らない。**後者を承知のうえで、入れない側を選ぶ。**

- **相手関係は、呼び出すときのメッセージで役に渡す。** 着順表をそのまま渡してよい
- **「DB だけを見ると相手関係が分からない」ことは、評価の本文に書き残す。** 後から読む人と
  役が、材料の欠けに気づけるようにする
- 同じレースを何度も参照するようになったら、そのとき全頭を入れる。**先回りして入れない**

### 裏取りの基準

**2回試して確からしい値が取れなければ、諦めて「取れなかった」と残す。**

- 数値（通過順・上がり3F・走破時計・斤量）が**判断の柱になるとき**は、別の情報源で突き合わせる
- **同じページから取れた他の項目が明らかに壊れていたら、そのページ全体を疑う。** 実在しない
  馬名や騎手名が混ざっていたら、数値も信じない
- 2回試して駄目なら**そこで止める。** 3つ目、4つ目と当たり続けない
- 取れなかったことは**評価の本文に書く。** 「この読みは裏の取れていない数値に乗っている」と
  明示して、後から読む人がそこを割り引けるようにする
- **取れなかった数値を、判断の柱に据えない。** 柱にするなら取り直す。取り直せないなら
  「材料が足りず判断できない」として扱う

### Phase 1 で DB を触る形（2026-08-09）

**最初の1レースは生SQLで登録する。** `getSql()` に直接 SQL を投げる。目的別の関数は作らない。

理由は、**関数に何が要るかは1レース登録してみないと分からない**ため。先に設計すると使われない

**したがって「1レース登録したあとに `lib/` の関数を切り出す」という宿題が残っている。**
面倒だったところを覚えておくこと。ここを飛ばすと生SQLのまま固定される。

`lib/` の切り方そのものは、この切り出しのときに決まる（下記「未確定事項」）。

1ディレクトリで置いている。**どこまでを1つの関心に含めるかは未確定**なので、あとで分けることに
なっても済むよう、どちらも DB に触らない純粋な計算だけにしてある。

| 用途 | 実装 |
| --- | --- |
| 買い目の展開 / 点数と金額 / 的中の判定 / 複勝の的中上限 / 回収率 | [lib/bets/](../lib/bets/) |
| レース名の正規化（全角→半角） | [lib/race-name/](../lib/race-name/) |
| 各列に入っていい値（[data-model.md](data-model.md#入っていい値) の16グループ） | [lib/enums/](../lib/enums/) |
| 印の表示 | **未実装。** 予想を入れる段階まで要らない |
| レース名の別名マスタ（「春天」→「天皇賞(春)」） | **未作成。** 略称の展開は1対1で決まらないのでマスタが要る |

| 用途 | やること |
| --- | --- |
| 買い目の展開 | `bet_legs` の列から実際の買い目を組み立てる。列の直積 → 同じ馬の重複を捨てる → マルチなら並べ替えを加える → 順不同の券種は顔ぶれで1点にまとめる |
| 点数と金額 | 展開した件数を `combination_count` に、`unit_amount × 件数` を `total_amount` に入れる。**手で入れない** |
| 的中の判定 | 「買った馬を着順の小さい順に並べたとき、i番目の着順が i 以下」。複勝とワイドだけ「n着以内に入っていればいい」型で別扱い |
| 複勝の的中上限 | 出走頭数が8頭以上なら3着、7頭以下なら2着 |
| 回収率 | `(payout + refund) ÷ total_amount` |
| 印の表示 | `marks` の `name` と `symbol` のどちらからでも引けるようにする |
| レース名の正規化 | 「春天」→「天皇賞(春)」。md マスタを引いてから SQL を投げる。あわせて**全角の括弧・数字・英字を半角へ寄せる**（JRA 公式サイトは全角括弧のため、写すと混ざる） |

**書くときに気をつける点が1つ。** 複勝の的中上限を出す「出走頭数」は、`entries.status` が
**取消・除外以外**の行数で数える。着順が入っている行だけを数えると、**中止**の馬が漏れて
頭数を1つ少なく見積もる。

## 決まっている運用

- **枠順確定直後**にエージェントを動かし、その時点で分かる範囲を記事化する
- 馬券は実際に買わず、**購入ポートフォリオだけ出力して擬似的に購入**し回収率を計測する
