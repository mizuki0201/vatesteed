# 評価は対象ごとに別テーブルへ分ける

- 日付: 2026-08-08
- 状態: 採用

## 背景

評価（文章）を書く先が7つある。出走・馬・血統・騎手・厩舎・コース・レース。7つとも形が
まったく同じで、**対象 + 内容 + 書いた人 + 更新日**しか持たない。

形が同じなら、1つのテーブルにまとめて「何についての話か」をカラムで持つこともできる。
テーブル数は7から1に減る。

## 決定

**7テーブルに分けたまま作る。**

## 検討したが採らなかった案

**1テーブルに統合し、対象の種類をカラムで持つ案。**

統合のメリットとして挙がったのは次の4つ。

- 同じ形のテーブルが7つ並ぶので、マイグレーションや読み書きのコードが7セット薄く重複する
- 「最近更新された評価を全部見る」のような横断の検索が、7テーブルを繋げる書き方になる
- 対象を増やすたびにテーブル追加が要る。統合ならカラムの値を1つ増やすだけ
- 将来ベクトル検索を入れる場合、統合なら埋め込みの列が1本で済む

採らなかった理由は3つ。

1. **統合すると、繋がりをDBが保証できなくなる。** 「対象の種類 + 番号」で指す形になるため、
   消えた馬を指したままでもエラーにならない
2. **横断検索の需要はまだ仮定の話。** Phase 1 で SQL を書くのは Claude Code なので、7テーブルを
   繋げる手間は実質的に無い
3. **ベクトル検索は導入自体が未確定**（[architecture.md](../architecture.md#ストレージで本当に効くもの)）。
   未確定の機能を理由に今の形を曲げるのは早い

加えて、`pedigree_notes` だけが持つ `scope` のような対象固有のカラムが、統合すると全行に付いて
ほとんどの行で空になる。

## 影響

- テーブル数が7つ増えるが、1つずつは小さい
- 対象を増やしたくなったとき（例: 馬主の評価）はテーブル追加の作業が発生する
- **馬と騎手の相性**のように複数の対象にまたがる評価は、専用テーブルを作らず `horse_notes` の
  文中で扱う。検索・集計はできなくなるが、それを許容する
