# 評価の本文は公開できるものだけにする

- 日付: 2026-08-18
- 状態: 採用

## 背景

馬の画面（`/horses/[id]`）は `horse_notes.body` をそのまま出している。閲覧レベルは今 friend だが、
**レベルは動かす前提で作ってある**（[architecture.md](../architecture.md#ディレクトリでレベルを分けない2026-08-16-決定)）。
member へ降ろせば、本文はそのまま読まれる。

ところが既にある評価には、分析したときの作業情報が混ざっていた。

- 「DB に出走は1つも無いので、以下は外部の記録を材料にしている」（オルフェーヴル）
- 「`pedigree_notes` が未登録なので、血統から読める素地との突き合わせはできていない」（同）
- 「産駒の傾向は `progeny_notes` の担当なので、ここには書いていない」（同）

**これは分析する役がオーケストレーターへ渡すための情報で、その馬の評価ではない。**
オルフェーヴルとディープインパクトだけでなく、複数のテーブルに同じ混入があった。

原因は指示の側にある。`horse-analyst` には「足りないものを言う」と「本文の案とは別に返す」の
両方が書いてあり、**どちらが保存されるのかが決まっていなかった。**
`pedigree-analyst` にだけ、行き先を分ける決まりが書いてあった。

## 決定

### `*_notes.body` は、member が単独で読める評価本文だけを持つ

書く時点の閲覧レベルで判断しない。**公開範囲を変えたときに本文を書き直さなくていい状態**にする。

### 非公開の本文カラムやメモ用のカラムは足さない

**アクセス制御で隠す形にしない。** `*_notes` を、公開できる評価だけが入っている場所にする。

### 分析する役の返答を「保存する本文」と「保存しないメモ」に分ける

見出しを固定して、取り違えられない形にする。オーケストレーターが DB へ書くのは前者だけ。
決まりは [agent-design.md](../agent-design.md#評価の本文と返すだけのメモ2026-08-18-決定) が正本。

### 内部構造を直接表す言葉を CHECK 制約で弾く

指示だけでは再発する。**保存される列すべて**に CHECK 制約を置き、テーブル名・役の名前・
`DB` のような**どう読んでも競馬の話にならない言葉**を弾く
（[0011](../../db/migrations/0011_notes_no_internal_terms.sql)）。かかるのは8テーブルの
`body` と、`pedigree_notes` `progeny_notes` の `scope`。

**`scope` を外さない。** 血統の側は馬の画面に本文と並べて出しており、**同じく公開される保存値**。
本文だけを守っても、隣に内部の言葉が残る。

**文脈までは判定しない。** 「未登録」「取れなかった」は競馬の側の意味（登録抹消、出走登録）と
重なるので入れない。そこは役の指示と、書く前の見直しで守る。

## 検討したが採らなかった案

**`/notes` を owner にして隠す。** 一覧の画面は owner だが、**馬・騎手・厩舎・コースの個別画面が
同じ本文を出している**ので、一覧を締めても分離できない。

**公開用と内部用の本文を2つ持つ。** 公開範囲を変えるたびにどちらを見せるかの判断が要り、
**二重管理と漏れを生む。** 内部用の本文は次の作業までしか使わないものなので、そもそも保存する
値打ちが無い。

**内部情報を `author` や別テーブルへ逃がす。** 保存する形はどれも同じ問題を持つ。返答の中だけに
置いて捨てる。

**制約を置かず、指示だけで守る。** 今回の混入は指示の穴から起きたが、**書き込みの経路が
`pnpm db:query` の生の SQL** なので、指示を直しても書ける状態が残る。書ける状態を塞ぐ。

**制約で文脈まで判定する。** 「未登録」「担当」のような言葉は競馬の意味と重なるため、弾くと
正しい本文まで書けなくなる。**制約は下限で、上限は指示で決める。**

## 影響

- [agent-design.md](../agent-design.md#評価の本文と返すだけのメモ2026-08-18-決定) に、対象を問わない
  決まりとして追加した。血統だけの決まりだった「書く内容と書かないもの」はそこへ吸収した
- [data-model.md](../data-model.md#body-は公開用の評価本文だけを持つ2026-08-18-追加) と
  [product.md](../product.md#画面) に、公開範囲との関係を書いた
- 分析する役7つの `instructions.md` に、返し方の形を入れた。**`scope` を持つ2つは、
  「保存する本文」「保存する範囲」「保存しないメモ」の3つに分ける。** 本文の中に `scope:` の行を
  混ぜる形にすると、本文へ書き込む経路に範囲の行まで入ってしまう
- `lib/notes/` に弾く言葉の一覧と判定を置き、単体テストで境界を確かめている。
  マイグレーションの SQL と一覧がずれないことも、同じテストで見ている
- **既にある評価を先に書き直してから制約を流した。** 制約は既存の行にも効くため
