# Vatesteed の開発体制

**この文書は、Vatesteed 自体の開発依頼のときだけ読む。** 競馬について対話する依頼では
読まず、[product.md](product.md) を正本にする。この文書は、開発依頼での役割・工程・
レビュー・受け入れの正本である。

**開発の役は、進行役・実装者・確認役という責務で定義する。** どのエージェントがどの役を担うか、
1つのエージェントで完結させるかは固定しない。現在の Codex と Claude Code の配置は、この文書の
後半にある暫定的な実行方法であって、役の定義ではない。競馬について対話するモードの役割や、
[product.md](product.md) の内容は、開発の実行方法のために変えない。

## 開発モードの入口

依頼が機能開発・不具合改修など、Vatesteed 自体を作るものであれば開発モードに入る。着手前に
次を読む。

- [product.md の「やらないこと」](product.md#やらないこと)
- [この文書の未決の問い](#未決の問い)
- `.claude/dev-context.local.md` があれば、その内容

最初の2つは、判断のしかたと何を作るかを混同しないために読む。特に、Vatesteed を特定の
レースを予想するためだけのものへ寄せない。

## 開発の役

複数のエージェントで進める場合は、次の責務を分ける。1つのエージェントで進める場合も、同じ
観点を順番に満たす。

| 担当 | 責務 | 担当しないこと |
| --- | --- | --- |
| **進行役** | 本人との対話、要件整理、設計、docs の正本化、実装依頼、差分レビュー、受け入れテスト、受け入れ判断、コミット | 実装者の完了報告だけで受け入れを決めない |
| **実装者（`dev-implementer`）** | 渡された docs と実装依頼に従うコード変更、単体テスト、`pnpm typecheck && pnpm test`、構造化した完了報告 | 設計判断、docs の正本化、コミット、本人との直接対話 |
| **確認役（`dev-reviewer` ほか）** | 依頼・docs・実装を突き合わせ、根拠を示してズレを指摘する | 受け入れを決める、実装を直接直す |

`dev-implementer` などの名前は役の名前であり、特定の製品やモデルを表さない。実行に使う
エージェントやモデルは、その時点の運用で選ぶ。

## 役の間で渡すもの

会話履歴を自動で共有できない実行方法では、次のものを渡す。単体で進めるときも、実装に入る前に
同じ内容を明確にする。

1. 進行役が先に更新した docs
2. 実装者に渡す実装依頼
3. 共有作業ディレクトリにあるコード差分とテスト結果
4. 実装者の構造化した完了報告

実装依頼は、実装者が過去の会話を見ない前提でも完結させる。必ず次を含める。

- 目的
- 正本となる docs と読む範囲
- 実装範囲
- 対象外
- 受け入れ条件
- 技術上の制約
- 完了報告の形式

## 1つの依頼が終わるまで

1. **進行役が要件と設計を整理する。** 未決の問いや本人にしか決められないことに当たれば、
   進行役が窓口として確認する。
2. **進行役が決まったことを docs に先に書く。** docs が正本で、実装はそこから導く。
3. **進行役が実装依頼を作る。** 上の必須項目を満たす依頼だけを実装者へ渡す。
4. **実装者が依頼を実行する。** 質問や未決の点があれば、進行役は推測で埋めず本人と整理し、docs と
   実装依頼を更新してから渡し直す。
5. **進行役が実物をレビューする。** 実装者の報告を受け取っただけでは完了にしない。共有作業
   ディレクトリの差分、変更されたファイル、実行結果を確認する。
6. **進行役が受け入れテストを行い、受け入れか差し戻しかを決める。** 差し戻すときは、正本 docs と
   具体的な不合格理由を再掲した新しい実装依頼を送る。
7. **進行役が受け入れ後にコミットする。** コミットや push をしてよいかは、その開発依頼で指定
   された範囲に従う。

## 進行役の必須レビューと受け入れ

レビュー工程は省かない。`dev-reviewer` が見る観点も、進行役の受け入れ前の必須確認に
移す。

- 実装が依頼と docs に一致し、依頼に無い変更を含まない
- [product.md の「やらないこと」](product.md#やらないこと)と未決の問いに反していない
- `AGENTS.md` の言葉づかい、コードの置き場所、テストの規則に従っている
- `lib/` のロジックには、実装の結果に合わせただけではない単体テストがある
- `.claude/agents/` を手で編集していない。役の変更は `agent/subagents/` を正本とし、
  `pnpm gen:agents` で生成している
- 共有作業ディレクトリの差分に、依頼と無関係な変更を混ぜていない
- 進行役自身が `pnpm typecheck && pnpm test` を実行し、必要な生成処理と受け入れ条件を確かめた

`dev-reviewer` は削除しない。進行役が必要と判断したときの独立した確認役として残すが、
受け入れの責任は常に進行役が持つ。`dev-explorer`、`dev-debugger`、`dev-agent-platform`、
`dev-web-platform` などの既存の開発役も、調査や原因究明の補助として残す。実運用で不要と
確認できるまでは削除しない。

## 実装者の完了報告

`dev-implementer` は、実装の最後に次の形で返す。

```text
状態: 完了 / 未完了
変更: ファイルごとの変更内容
テスト: 実行したコマンドと結果
未解決: 残っている問題・質問。無ければ「なし」
対象外: 触れなかったもの
```

これは進行役のレビューを省くためのものではない。進行役が差分とテスト結果を確認するための
入口である。

## 役の正本と生成

開発役の正本は `agent/subagents/<id>/` にある。役の名前と責務はここで定義し、実行に使う
エージェントへ渡す。Claude Code を使うときの `.claude/agents/<id>.md` は生成物であり、
直接編集しない。

```bash
pnpm gen:agents
```

Claude Code で役を実行する場合は、役の正本を変えたらこのコマンドで生成し直す。起動済みの
Codex タスク経由で Claude Code を呼ぶ場合は、更新前の役定義を持っていることがあるため、
新しいタスクで確認する。

## 開発時の実行方法（暫定）

この節は**Vatesteed 自体を作る依頼だけ**に適用する。**本人から実行元について明示の指示が無い
限り、Codex を進行役、Claude Code を `dev-implementer` の実行元として使う。** 変更の規模や
単純さを理由に Codex 単体へ切り替えない。Codex は要件整理、docs の正本化、実装依頼、受け入れを
担い、Claude Code はコード変更と完了報告を担う。

本人が Codex 単体で完結するよう明示したときなどは、その指示に従う。この配置は役の定義ではなく、
現在試している実行体制であり、運用が変わればこの節を更新する。競馬について対話する依頼で分析する役を
使う際の既定は [claude-code-bridge.md](claude-code-bridge.md) を参照する。

この配置では、Codex が docs と実装依頼を渡し、Claude Code がコード変更と完了報告を返す。Codex は
差分とテスト結果を確認して受け入れを判断する。

### Codex から Claude Code を呼ぶ開発時の接続確認

開発時も、[Codex から Claude Code を呼ぶ](claude-code-bridge.md) の手順を使う。新しい Codex タスクでは、
docs やコードを変更する前にファイル操作をしない最小の接続確認を1回行う。認証はこのリポジトリの
`.claude/settings.local.json` に閉じ、呼び出しは `pnpm claude:opus` で Opus に固定する。

接続確認で Opus と認証が確認できなければ実装を始めない。失敗時に Keychain、API キー、既定モデルへ
切り替えることはしない。

## タスク

やることは `docs/tasks/` に1タスク1ファイルで置く。読み書きの手順は `task-management` スキルが
正本である。着手・完了・保留などの状態が変わったときは、該当タスクを更新する。

## 未決の問い

**勝手に確定させない。** 作業中にここに当たったら、その場で決めず、必要な判断を本人へ返す。

1. **「人間の読みを勝手に上書きしない」を完成形でどう扱うか。**
   [product.md の該当節](product.md#人間の読みは勝手に上書きしない)と
   [学習の段階](concept.md#学習の段階)の完成形が、そのままでは両立しない。
2. 予想の実行を始めるきっかけをどう検知するか。
3. オーケストレーターの `instructions.md` に何を置くか。
4. 調教の仕上がりをどの情報源からどう判断するか。
5. エージェントの自律的提案の枠組みをどこまでにするか。
6. 記事生成の流れをどう作るか。
7. 自分の購入を実際の馬券購入とするか、AI と同じく擬似とするか。
8. `lib/` の切り方を、最初のレースを登録した後にどう決めるか。
