# Vatesteed の開発体制

**この文書は、Vatesteed 自体の開発依頼のときだけ読む。** 競馬について対話する依頼では
読まず、[product.md](product.md) を正本にする。この文書は、開発依頼での役割・工程・
レビュー・受け入れの正本である。

このモードでは **Codex が PM、Claude Code が実装者** である。競馬について対話するモードの
役割や、[product.md](product.md) の内容は、この体制のために変えない。

## 開発モードの入口

依頼が機能開発・不具合改修など、Vatesteed 自体を作るものであれば開発モードに入る。着手前に
次を読む。

- [product.md の「やらないこと」](product.md#やらないこと)
- [この文書の未決の問い](#未決の問い)
- `.claude/dev-context.local.md` があれば、その内容

最初の2つは、判断のしかたと何を作るかを混同しないために読む。特に、Vatesteed を特定の
レースを予想するためだけのものへ寄せない。

## 役割

| 担当 | 責務 | 担当しないこと |
| --- | --- | --- |
| **Codex（PM）** | 本人との対話、要件整理、設計、docs の正本化、Claude への実装依頼、差分レビュー、受け入れテスト、受け入れ判断、コミット | Claude の完了報告だけで受け入れを決めない |
| **Claude Code（`dev-implementer`）** | 渡された docs と実装依頼に従うコード変更、単体テスト、`pnpm typecheck && pnpm test`、構造化した完了報告 | 設計判断、docs の正本化、コミット、本人との直接対話 |

Claude のモデルは `agent/subagents/dev-implementer/agent.ts` で
`anthropic/claude-opus-5` に固定する。Codex は MCP の呼び出しでモデルを上書きしない。

## Codex と Claude の間で渡すもの

会話履歴は渡さない。共有するものは次の4つだけである。

1. Codex が先に更新した docs
2. Codex が MCP に渡す実装依頼
3. 共有作業ディレクトリにあるコード差分とテスト結果
4. Claude の構造化した完了報告

実装依頼は、Claude が過去の会話を見ない前提で完結させる。必ず次を含める。

- 目的
- 正本となる docs と読む範囲
- 実装範囲
- 対象外
- 受け入れ条件
- 技術上の制約
- 完了報告の形式

## 1つの依頼が終わるまで

1. **Codex が要件と設計を整理する。** 未決の問いや本人にしか決められないことに当たれば、
   Codex が窓口として確認する。
2. **Codex が決まったことを docs に先に書く。** docs が正本で、実装はそこから導く。
3. **Codex が実装依頼を作る。** 上の必須項目を満たす依頼だけを送る。
4. **Codex が Claude を同期で呼ぶ。** 呼び出しは次の条件に固定する。

   ```text
   claude_code.Agent
   subagent_type: "dev-implementer"
   run_in_background: false
   ```

   Claude が質問や未決の点を返したら、Codex は推測で埋めず本人と整理し、docs と実装依頼を
   更新してから新しい依頼として送り直す。
5. **Codex が実物をレビューする。** Claude の報告を受け取っただけでは完了にしない。共有作業
   ディレクトリの差分、変更されたファイル、実行結果を確認する。
6. **Codex が受け入れテストを行い、受け入れか差し戻しかを決める。** 差し戻すときは、正本 docs と
   具体的な不合格理由を再掲した新しい実装依頼を送る。
7. **Codex が受け入れ後にコミットする。** コミットや push をしてよいかは、その開発依頼で指定
   された範囲に従う。

## Codex の必須レビューと受け入れ

レビュー工程は省かない。以前 `dev-reviewer` が見ていた観点を、Codex の受け入れ前の必須確認に
移す。

- 実装が依頼と docs に一致し、依頼に無い変更を含まない
- [product.md の「やらないこと」](product.md#やらないこと)と未決の問いに反していない
- `AGENTS.md` の言葉づかい、コードの置き場所、テストの規則に従っている
- `lib/` のロジックには、実装の結果に合わせただけではない単体テストがある
- `.claude/agents/` を手で編集していない。役の変更は `agent/subagents/` を正本とし、
  `pnpm gen:agents` で生成している
- 共有作業ディレクトリの差分に、依頼と無関係な変更を混ぜていない
- Codex 自身が `pnpm typecheck && pnpm test` を実行し、必要な生成処理と受け入れ条件を確かめた

`dev-reviewer` は削除しない。Codex が必要と判断したときの独立した確認役として残すが、
受け入れの責任は常に Codex が持つ。`dev-explorer`、`dev-debugger`、`dev-agent-platform`、
`dev-web-platform` などの既存の開発役も、調査や原因究明の補助として残す。実運用で不要と
確認できるまでは削除しない。

## Claude の完了報告

`dev-implementer` は、実装の最後に次の形で返す。

```text
状態: 完了 / 未完了
変更: ファイルごとの変更内容
テスト: 実行したコマンドと結果
未解決: 残っている問題・質問。無ければ「なし」
対象外: 触れなかったもの
```

これは Codex のレビューを省くためのものではない。Codex が差分とテスト結果を確認するための
入口である。

## 役の正本と生成

開発役の正本は `agent/subagents/<id>/` にある。Claude Code が読む `.claude/agents/<id>.md` は
生成物であり、直接編集しない。

```bash
pnpm gen:agents
```

役の正本を変えたら、このコマンドで生成し直してから新しい Codex タスクで確認する。起動済みの
Codex タスクは、更新前の MCP の役定義を持っている場合がある。

## MCP の接続確認

実装依頼を送る前に、新しい Codex タスクでファイル操作をしない短い呼び出しを行う。
`claude_code.Agent` が使え、`subagent_type: "dev-implementer"` と
`run_in_background: false` を受け付けることを確かめる。

Claude の利用上限エラーが返る場合は、Vatesteed 専用の Keychain 認証までは到達している。
一方、`Agent type 'dev-implementer' not found` のように役の定義を見つけられない場合は、
実装を始めない。MCP と Claude Code の設定読み込み状況を報告し、呼び出せる状態を直してから
新しい Codex タスクで再確認する。

`launch-claude-mcp` は Keychain から取得した `CLAUDE_CODE_OAUTH_TOKEN` を、その呼び出しだけに
渡す。MCP の `Agent` は、プロジェクトを作業場所にして `claude --agent <役名> -p` を同期実行する。
この経路では `.claude/agents/` の生成物が Claude Code に読まれ、役のモデル指定も使われる。

## タスク

やることは `docs/tasks/` に1タスク1ファイルで置く。読み書きの手順は `task-management` スキルが
正本である。着手・完了・保留などの状態が変わったときは、該当タスクを更新する。

## 未決の問い

**勝手に確定させない。** 作業中にここに当たったら、その場で決めず、必要な判断を本人へ返す。

1. **「人間の読みを勝手に上書きしない」を完成形でどう扱うか。**
   [product.md の該当節](product.md#人間の読みは勝手に上書きしない)と
   [学習の段階](concept.md#学習の段階)の完成形が、そのままでは両立しない。
2. 集めるスキルをどう配るか。分析する役が集めた材料で文脈が圧迫し始めたときに決める。
3. 予想の実行を始めるきっかけをどう検知するか。
4. オーケストレーターの `instructions.md` に何を置くか。
5. 調教の仕上がりをどの情報源からどう判断するか。
6. エージェントの自律的提案の枠組みをどこまでにするか。
7. 記事生成の流れをどう作るか。
8. 自分の購入を実際の馬券購入とするか、AI と同じく擬似とするか。
9. `lib/` の切り方を、最初のレースを登録した後にどう決めるか。
