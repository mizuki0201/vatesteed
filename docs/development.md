# 開発の進め方（Vatesteed 自体を作る側）

**このドキュメントは「Vatesteed をどう作るか」の正本。** 「Vatesteed が何であるか」は
[product.md](product.md) にある。**両者を混ぜない。**

- product.md — 競馬について対話するエージェントとして、何をするものか
- このファイル — そのエージェントを作る作業を、どういう体制で回すか

---

## 2つのモード

**同じリポジトリの中に、性質の違う2つの働き方が同居している。**

| | 競馬について対話する | Vatesteed 自体を作る |
| --- | --- | --- |
| きっかけ | 予想したい・気になった・レースが終わった | 作りたいもの・直したいものが出てきた |
| 窓口 | オーケストレーター | **同じオーケストレーター** |
| 下で動く役 | 分析する役（`entry-analyst` ほか） | 開発の役（`dev-` で始まるもの） |
| 正本 | product.md ほか `docs/` | このファイル |
| 成果物 | 各 `*_notes` / 予想 / 記事 | docs の差分 / コード / `docs/tasks/` |

**人間が話す相手はどちらのモードでも同じ1つ。** サブエージェントの側にもう1つ
オーケストレーターを置く形にはしない。理由は3つある。

- **サブエージェントは人間と直接やり取りできない。** 開発の依頼は話しながら決めるものなので、
  中に閉じ込めると質問のたびに往復が挟まる
- **eve の宣言サブエージェントは root から何も継承しない。** instructions・tools・skills・
  connections・sandbox がすべて自前になり、必要なものを配下に複製することになる
- **root の組み込みの `agent` ツールは root 専用。** サブエージェントに降ろすと、その場で
  子を起こす手段を失う

### モードの出し分け

**Phase 1 では機械的に出し分けられない。** `.claude/agents/` に置いたものは常にすべて
オーケストレーターから見える。名前の接頭辞（`dev-`）と description で区別するだけなので、
**モデルの判断に頼っている**。

Phase 3 では eve の `defineDynamic` に置き換える。`session.started` / `turn.started` で
解決して `null` を返せば、その役は親から見えなくなる。

**グループ用のディレクトリを1段挟むことはできない。** eve はディレクトリ名がそのまま役の
名前になるため、`subagents/dev/implementer/` と書くと `dev` が `agent.ts` の無い役として
扱われる。分けるなら名前の接頭辞。

## コンセプトを外さないための二重の歯止め

**設計の判断で最も起きやすい失敗は、Vatesteed を「レース予想アプリ」として扱うこと。**
2026-08-11 のセッションでは、これを1回のセッション中に3回踏んで指摘を受けている。

判断のしかたを整えても、これは直らない。**判断のしかたと、何を作るかは別のもの。** そこで
入口と出口の両方に置く。

1. **入口** — 開発の依頼を受けたら、着手する前に
   [product.md のやらないこと](product.md#やらないこと)と
   [未決の問い](product.md#未決の問い)を読む
2. **出口** — `dev-reviewer` の定型の観点に「やらないことに触れていないか」を入れる

片方だけでは必ず抜ける。

## 開発の役

**書くのは `dev-implementer` だけ。** 他の役は調べて返すだけで、ファイルを書かない。
このリポジトリはワークツリーを作らず `main` の上で直接実装する運用なので、**複数の役が同時に
同じ作業ツリーを触ると壊れる**。書き手を1人に絞るのが唯一安全な形。

| 役 | 何をする | 書くか |
| --- | --- | --- |
| `dev-explorer` | リポジトリと docs の中の事実を集める | 書かない |
| `dev-implementer` | 渡された指示のとおりに書き、テストを通す | **書く** |
| `dev-reviewer` | 指示・docs・コンセプト・言葉づかいと突き合わせる | 書かない |
| `dev-agent-platform` | eve と Claude Code についての専門家 | 書かない |
| `dev-web-platform` | Next.js / Vercel / shadcn についての専門家 | 書かない |
| `dev-debugger` | 不具合の原因を突き止める | 書かない |

役の実体は `agent/subagents/<id>/` にあり、手順の正本は各役の `instructions.md`。
`.claude/agents/` は `pnpm gen:agents` が生成する（[architecture.md](architecture.md) 参照）。

### 調べる役を3つに分けている理由

`dev-explorer` は**このリポジトリの中**だけを見る。`dev-agent-platform` と
`dev-web-platform` は**外の技術**を見る。調べ先も判断のしかたも違うので、1つにまとめると
何でも屋になって深さが出ない。

専門家を eve / Claude Code と Next.js / Vercel の2つに割っているのも同じ理由。
Neon や SQL の専門家は**今は置かない**。スキーマは
[data-model.md](data-model.md) で確定していて、マイグレーションの仕組みもできている。
必要になったら足す。

### 原因究明と修正を分けている理由

`dev-debugger` は原因と再現の手順までを返し、**直さない**。同じ役に両方やらせると、
直す方に急いで原因を外す。

**この役は確度が低い。** この体制で不具合改修をまだ1度もやっていないため、要るという判断が
実績に基づいていない。使ってみて要らなければ落とす。

### 置かない役

| 役 | 置かない理由 |
| --- | --- |
| docs を書く役 | docs は「何を・なぜ」の正本で、判断そのもの。オーケストレーターが書く |
| テストを設計する役 | `dev-implementer` が書き、`dev-reviewer` が観点で見れば足りる |
| タスク管理の役 | `task-management` スキルで足りる |

### 委任するときに渡すもの

**判断の基準は、オーケストレーターの頭の中にあるだけでは委任先に届かない。** 指示文に、
そのタスクに効く基準を書き込んで渡す。`dev-reviewer` にも、見るべき観点をその都度渡す。

モデルは呼び出しのたびに明示する。判断や理解の深さが要る役には強いモデルを、収集や整形だけの
役には軽いモデルを充てる。

## 1つの依頼が終わるまで

**docs が正本、実装は docs から導く**（[docs/README.md](README.md#docs-を正本とする変更の流れ)）。
この順序は開発モードでも変わらない。

1. 何を作るかを対話で決める
2. **決まったことを先に docs に書く**
3. その差分から実装を導く
4. `pnpm typecheck` と `pnpm test` を通す
5. コミットする

**4 を飛ばして終わりにしない。** 通らなかったら、通るまで直すか、何が起きたかをそのまま伝える。

### 止まるところ

**基本は止まらずに進める。** 止まるのは次の場合だけ。

- **未決の問いに当たったとき。** その場で決めず、
  [product.md の未決の問い](product.md#未決の問い)に1行足して止まる
- **人間にしか無いものが要るとき。** 判断の材料が人間の側にしか無いなら聞く
- **履歴を書き換える操作。** force push・`git reset --hard`・ブランチの削除は必ず手前で確認する
- **消す操作。** ファイル・データの削除、戻せない上書き

コミットとプッシュは自由に行ってよい（[AGENTS.md](../AGENTS.md#開発の進め方git)）。

## タスク

やることは `docs/tasks/` に1タスク1ファイルで置く。手順は `task-management` スキルが正本。

- 会話の中でやることが出てきたら、タスクに切っていいかを確認する
- **着手・完了・保留など状況が変わったら、言われなくても該当タスクを更新する**
- `docs/tasks/` は gitignore 済み。手元だけの作業リストで、消えても git からは戻せない

---

## 未決の問い

**勝手に確定させない。** 作業中にここに当たったら、その場で決めずに1行足して止まる。

**ここに並ぶのは作り方についての未決だけ。** Vatesteed が何であるかについての未決は
[product.md の未決の問い](product.md#未決の問い)にある。どちらに足すか迷ったら、
**「Vatesteed を使う人に関係するか」**で分ける。関係するなら product.md、
作る側だけの話ならこちら。

1. 開発のために外のサイト（技術ドキュメントなど）を見てよいか。
   [compliance.md](compliance.md) の自動アクセス禁止リストは競馬の情報源を想定して
   書かれているが、「リストが空のうちは自動アクセスしない」が開発の調べものにも効くのかを
   決めていない。**当面は手元に入っている版のドキュメントだけを読む**
2. `dev-debugger` を残すか。原因究明と修正を分ける形が実際に効くかを、まだ確かめていない
3. Phase 1 でモードを機械的に出し分けられない件を、このまま Phase 3 まで引くか。
   接頭辞と description だけに頼っているので、誤って呼ばれる余地がある
