# Vatesteed とは何か（最上流）

**このドキュメントは Vatesteed の最上流の正本。** 「何にしたいか」「普段どういう運用をするか」を
ここに書く。他のドキュメントはすべて、ここに書かれたことの詳細か背景にあたる。

思想の背景は [concept.md](concept.md)、技術構成は [architecture.md](architecture.md)、
スキーマは [data-model.md](data-model.md)、スキルの設計は [agent-design.md](agent-design.md)。

## このドキュメントの扱い方

- **随時更新していく。** 一度書いて固定するものではない。運用してみて違えば書き換える。
  「今はこう決まっている」を写したものであって、将来の約束ではない
- **エージェントや画面の挙動を変えたくなったら、まずこのドキュメント（と下位のドキュメント）を
  直す。** 実装から先に変えない。docs を直す作業だけを人間と AI の対話で行い、
  `agent/` と `app/` の修正はその差分から導く
- **確定と未確定を混ぜない。** 未確定のものは「未決の問い」に置き、勝手に確定させない
- 列挙は、断りがない限り例示であって網羅ではない

## 何であるか

競馬について、**AI と人間が分担して考えるためのエージェント**。

着順・タイム・人気は結果であって、能力や状態そのものではない。数字の背後にある文脈・経緯・
事情を読み取って評価を補正する過程を、構造化して扱えるようにする。詳しくは
[concept.md](concept.md)。

**中心にあるのは「競馬について対話すること」。** 対象は馬・騎手・厩舎・コース・血統・レースなど
何でもよく、時間軸も問わない。特定のレースの予想は、その中の**1つの形**にすぎない。

### 位置づけ

| | 内容 |
| --- | --- |
| 本線 | 自分が競馬を楽しむための補助ツール + 個人開発を楽しむための題材 |
| サブ | 認知獲得 → 将来的に note 等での有料販売 |
| 目指す先 | **最終的な完全自動化。** 人間の思考を模倣し、対話の中から自分で学習して精度を上げていく |

**目指す先へ一足飛びには行かない。** 初期は精度を上げるために人間が意識して知見を渡すが、
完成形では人間に「教えるための作業」を発生させない。段階の考え方は
[concept.md](concept.md#学習の段階) が正本。

### やらないこと

- **回収率を売らない。** 売るのは予想の裏側にある AI の思考回路
- **結論そのものを正解として固定しない。** 人間が過去に出した答えを覚えるのではなく、同じ
  材料から同じように考えられるようにする。本人の実例は「どんな情報が必要かを示す材料」として
  扱う（→ [concept.md](concept.md#コアコンセプト)）
- **今の分担を最終形として作らない。** 人間が手を動かす前提で固めた作りは、AI 側へ寄せる
  ときに作り直しになる
- **レース予想アプリにしない。** 予想は用途の1つであって、全部ではない。設計の判断に迷ったとき、
  「特定のレースを予想する」ことに寄せた答えを選ばない

### 分担の線は動く

「今は人間がやっている」ことを、そのまま「人間がやるべきこと」として固定しない。蓄積が
進むにつれて AI 側へ寄せていく。**人間が「あまり意識していない」と答えた領域は、対象外では
なく AI に寄せる候補**として扱う。

**寄せ切った先が完全自動化にあたる。** 今すぐ移せないもの（映像を見た印象など）は、AI の側に
入力の経路が無いだけで、「人間がやるべきこと」ではない。

## エージェントの形

**人間との対話、情報収集、登録・分析・予想、文章確認の担当は固定しない。** 1つのエージェントが
すべてを担っても、複数のエージェントで分けてもよい。人間が分析する役や検証する役と直接やり取り
するかも、そのときの運用で決める。

**現在の Phase 1 の Codex から Claude Code へ渡す経路では、Codex が人間との対話・情報収集・
事実のDB登録・文章確認、Claude Code が分析・予想とその結果の保存を担う。** Vatesteed 自体を
作る依頼では、Claude Code は実装を担う。Claude Code に調査や事実登録まで持たせず、分析または
実装へ使う。これは暫定の配置であり、本人が実行元を指定した場合はその指示を優先する。

Codex から Claude Code へ渡す場合、Codex は依頼を理解するためだけでなく、分析に必要な
事実を先に調べ、登録範囲に入る事実だけをDBへ登録して読み直す。馬の登録と分析なら、対象の特定、
指定された範囲の出走歴、最低限の血統、レースや血統に関する参考情報がこれに含まれる。これは依頼に
応じた例であり、全依頼に同じ項目を固定しない。出典、確認時点、確認できた事実、食い違い、取れなかった情報、
DBへ登録して読み直した結果をタスクMarkdownへ残し、準備が終わる前に Claude Code へ渡さない。

**調査で確認した事実を、すべてDBへ入れるわけではない。** 登録するのは今回の分析対象に直接属し、
分析結果を保存するために必要な事実だけ。分析対象の血統を読むための先祖、過去のレースで一緒に
出走した他馬、そのレースの払戻などは、調査資料としてClaude Codeへ渡してよいが、関連している
だけでは登録しない。

別の分析でも使うことが明白で、特定の開催日や一時的な状態に依存しない一般情報は登録してよい。
コースの形や直線の長さのように、同じ条件を扱うたびに使う内容がこれにあたる。これは例示であり、
固定の一覧ではない。使い回せるか判断がつかないものはDBへ入れず、今回の調査資料だけに残す。

Claude Code はタスクMarkdownとDBを照合して分析する。不足や誤りの疑いが判断に影響するときは、
対象、必要な事実、その事実を使う判断をCodexへ返し、自分で追加調査や事実登録をしない。Codexが
調査・登録・読み直しを終えた後、同じClaude Codeセッションを再開する。

- **情報を集める役は、問いを整理し、外部サイトと動画から材料を集める。** 評価・印・買い目を
  決める役と分けてもよい
- **分析を担う役は、渡された調査資料と DB を基に、分析・予想とその結果の保存を進める。**
  材料不足が判断に効くときは、必要な事実と用途を人間との対話を担う役へ返す
- **会話だけで済むこと、DBを引くだけで済むことは、いま分析を担っている役自身が答える。**
  何でも分割しない
- **広範囲の分析が必要なとき、または手順を分けて分担した方がよいときは、分析を担う役が
  「分ける」と判断し、自分は指示役に回る**
- 指示役に回った役は、必要な作業を洗い出し、役割を分けてサブエージェントに
  任せ、返ってきた結果を統合する
- **対象や材料が多いことだけを理由に役を増やさない。** 依頼ごとに決めた分析単位と実行上限の
  中で、同じ役が複数の材料をまとめて扱う。並列にする必要があるときも、実行上限を超える役を
  起動しない
- **人間に聞く必要があることと、追加で確かめる必要があることは、人間との対話を担う役が窓口になる**

Phase 1 の Codex から Claude Code への入口は子エージェントを禁止している。この経路で複数の
専門役が必要な依頼を実行するときは、オーケストレーターとして1つのClaude Codeセッションを使い、
必要な役の指示を読んで作業を順番に行う。役を分けることを、Claude Codeのセッション数を増やす
ことと同一視しない。

登録本文・返答文は、文章確認を担う役が造語、不自然な比喩、根拠より強い断定、事実と読み取りの
混同を確認する。修正は分析を担った役が行い、文章確認を担う役は評価・印・買い目を直接書き換えない。

この形は運用によらず同じ。決まった手順を持つ運用（2 予想 / 3 振り返り）でも、開き放しの問い
（1 対話）でも変わらない。違うのは手順が決まっているかどうかだけで、**開き放しの問いのために
専用の進行役スキルを作るのではなく、オーケストレーターがその場で作業を組み立てる**。

**役は「分析する役（対象ごと）」と「検証する役」の2つ。外部情報を集める役は必要に応じて置く。**
分け方の詳細と経緯は [agent-design.md](agent-design.md#サブエージェントの使い分け) を参照。

## 運用の一覧

> **2026-08-11 に合意。** ただし固定ではなく、運用してみて違えば書き換える。

Vatesteed の運用の中心は **「競馬について対話する」**（1）。特定のレースの予想（2）と
振り返り（3）は、**きっかけと成果物の形が決まっている、対話の特殊な形**として扱う。

**この順序を崩さないこと。** 予想を中心に置くと「レース予想アプリ」になる。

**ここに並ぶのは、Vatesteed を使って競馬に向き合うときの運用だけ。** Vatesteed 自体を作る
作業は製品の説明ではないので、[development.md](development.md) に分けてある。

### 1. 競馬について対話する（中心）

| | |
| --- | --- |
| きっかけ | 気になったとき。いつでも |
| 対象 | 馬・騎手・厩舎・コース・血統・レース、あるいはそれらをまたぐ問い |
| 時間軸 | 問わない。過去の再検討 / 目の前のレース / 先の展望 |
| 人間 | 問いを出す。データに表れない文脈を渡す。結論をすり合わせる |
| AI | 蓄積を読んで材料を出し、考えを組み立てて答える |
| 成果物 | 会話そのもの。決まったことは各 `*_notes` へ残す |
| 関係するスキル | horse / jockey / trainer / course / pedigree / entry / race-analysis を必要に応じて |

問いの例（**例示であって網羅ではない**）:

- この馬は距離を延ばして良くなるか
- 今年の凱旋門賞に出る日本馬は勝てそうか
- この厩舎は叩き2走目で本当に動くのか
- 去年のあのレースは、いま見るとどう評価すべきか

**この形の対話に専用の進行役スキルは作らない。** オーケストレーターがその場で作業を組み立て、
必要なら分担する（→ [エージェントの形](#エージェントの形)）。register-race / review-race は
どちらも決まった手順を通し切るためのもので、開き放しの問いには使わない。

**問いを投げる導線は Claude Code 経由。** 対話そのものをスマホから始める形は想定しない。
**外で見かけた話をその場で残すだけ**なら、[画面](#画面)に受け皿がある
（→ [見かけた話を残して、後で確かめる](#見かけた話を残して後で確かめる)）。

### 2. レースを予想する（1の特殊な形）

対話のうち、**きっかけ・締切・成果物の形が決まっているもの**。

| | |
| --- | --- |
| きっかけ | 枠順確定直後（**検知方法は未決**） |
| 人間 | 対象レースを選ぶ。取得内容を確認する。解釈を足す |
| 情報を集める役 | 情報を集め、分析対象に直接属する事実だけをDBへ登録して読み直し、参照だけする関連情報・出典・不足を整理する |
| 分析を担う役 | 登録済みの事実を使って各馬を評価し、展開と着順を予想し、買い目を組む |
| 成果物 | `ai_predictions` `race_predictions` `race_prediction_conditions` `ai_bets` / note 記事 |
| 関係するスキル | register-race → 各分析 → predict-race → plan-bets |

**出した予想は、出した時点で固定する。** 枠順が確定する金曜か土曜に作り、日曜のレース前に出す。
**当日の馬場を見てから公開済みの予想・買い目・記事を書き直さない。** 当日の話は運用1の対話として
扱う（理由と、予想時点の前提をどこに置くかは
[agent-design.md](agent-design.md#ラップと予想時点の前提2026-08-17-決定)）。

馬券は実際に買わず、**購入ポートフォリオだけ出力して擬似的に購入**し回収率を計測する。
**1レースあたりの予算は 2,000円で固定**し、レースの格や自信度で変えない（理由と手順は
[agent-design.md](agent-design.md#5-買い目を組む)）。

**各馬を読み終わるまで展開を組み始めない**、**展開は各時点の隊列まで出す**といった順序と
粒度は [agent-design.md の予想の手順](agent-design.md#予想の手順2026-08-15-決定) が正本。

### 3. 振り返る（レース後）

こちらも対話の特殊な形。レースが終われば必ず起きる。

| | |
| --- | --- |
| きっかけ | レースが終わったあと |
| 人間 | 走りを見た印象・レース後のコメントの含意を渡す。評価をすり合わせる |
| AI | 結果を取り込み、そのレースと各出走を評価したあと、各馬のまとめで結論が変わる項目だけを更新する |
| 成果物 | `entry_notes` `race_notes` と、差分がある馬の `horse_notes` ほか |
| 関係するスキル | review-race → race-analysis / entry-analysis / horse-analysis |

### 4. 自分でも予想する（AI とは別線）

| | |
| --- | --- |
| きっかけ | 自分が予想したいとき |
| 人間 | 自分の印と購入を記録する |
| AI | 記録を受け取って `my_*` テーブルに入れる |
| 成果物 | `my_predictions` `my_bets` |

**自分の購入はエージェントの学習に自動反映しない。** AI = 膨大なデータから推論して当てにいく /
自分 = 趣味として楽しみ推し活もする、という役割分担のため。反映したいと判断したときだけ、
明示的にスキルを叩く。

### 5. 発信する

| | |
| --- | --- |
| きっかけ | 予想を出したとき / 振り返ったとき / 開発で決定・実装・解決があったとき |
| 人間 | 出す判断をする。内容を確認する |
| AI | 予想や振り返りや開発の記録を記事・投稿の形にする |
| 成果物 | note 記事 / Zenn 記事 / X 投稿 |
| 関係するスキル | write-note-article / write-zenn-article / write-x-post |

詳細は [publishing.md](publishing.md)。

## 常に働くこと

上の運用と並ぶものではなく、**どの運用の中でも常に働く振る舞い**。特定の手順の中だけで
起きるものとして設計しない。

### 学んで残す

**すべての会話が学習の機会。** 「ナレッジを溜める時間」や「反省会」を別に設けるのではなく、
どの会話であっても、そこで何かが決まったなら残す。

残す先は2つある。**何についての学びかで決まる。**

| 残す先 | 何を | 上書きの単位 |
| --- | --- | --- |
| ナレッジDB（各 `*_notes`） | 競馬についての知識・解釈 | 1対象1行の上書き。履歴は持たない |
| `docs/` と `agent/skills/` | 自分の判断のしかた・手順の誤り | 該当箇所を書き換える |

- **人間**: データに表れない文脈を渡す。AI の案をすり合わせて結論を出す。修正を承認する
- **AI**: 過去の評価を読んで案を出す。決まった結論を書き込む。自分の判断の誤りに気づいたら
  docs とスキルを直す
- 関係するスキル: improve-agent（判断の誤りを特定して直す側）

**日々改善を加え続けること自体をプロジェクトの本質に据える。** 毎週レース結果という
フィードバックが得られるドメインなので相性が良い。ただし改善のきっかけは予想のズレだけでは
なく、**普段の対話の中で「その見方は違う」と分かった瞬間も含む**。

**学習は、いずれ対話の裏に回す。** 今は「ここを覚えておいて」と人間が意識して渡す形だが、
目指すのは**人間が普通に競馬の話をしているだけで学習が進む形**
（→ [concept.md](concept.md#学習の段階)）。**今の書き方を最終形として設計しない。**

### 見かけた話を残して、後で確かめる

**材料が入ってくるのは、対話している時とは限らない。** SNS などで見かけた話は、その場で
残せなければ消える。**残すことと、確かめて評価に反映することを、別の時点に分ける。**

| | 誰が | 何をするか |
| --- | --- | --- |
| 残す | 人間 | 見かけた話を[画面](#画面)から1つ入れる。**分類も判断もしない** |
| 確かめる | AI | 蓄積と突き合わせ、足りなければ調べ、宛先を決めて書く |

- **入るのは材料であって評価ではない。** [`memos`](data-model.md#memos) に置かれ、
  **そこから評価へ自動でつながる経路は作らない**
- **取り込みは対話の中で行う。** 人間が居ないところで走らせない。人間が渡した材料を AI が
  単独で評価に変える形になり、[人間の読みは、勝手に上書きしない](#人間の読みは勝手に上書きしない)が
  効かなくなる
- **宛先が無いものは待たせる。** 外で見かける話の多くは「今週のあの馬」で、その出走はまだ
  DB に無い。**取り込みを1回で終わる処理として設計しない**
- 手順は [agent-design.md](agent-design.md#メモの取り込み2026-08-22-決定)、関係するスキルは
  intake-memos

**これも今の形であって、目指す形ではない。** 人間が手で入れているのは、AI の側に「外で
流れている話を見る」経路が無いから（→ [分担の線は動く](#分担の線は動く)）。

### 人間に何を聞くか

**承認は求めない。** 「登録していいですか」「この処理を実行していいですか」は聞かない。
AI が自分で判断できることは、聞かずにやる。

**聞くのは、人間にしか無いものだけ。** 映像を見て気づいたこと、コメントの含意、陣営の事情、
遠征の経緯。**数字からは出てこない部分**にあたる。ここを取りこぼすと、このプロジェクトの
中核（[concept.md](concept.md)）が失われる。

**聞く範囲は縮んでいく。** 「人間にしか無いもの」は固定の一覧ではなく、AI の側に入力の経路が
できた分だけ減る。**問いを減らす方向に設計する**（→ [concept.md](concept.md#学習の段階)）。

- **問いは開いた形にする。** 「これでいいですか」ではなく「ここが分からなかった」
  「ここが引っかかる」と差し出す。Yes / No で閉じる問いは、人間が何も足せない
- **問いを出しても止まらない。** 分かる範囲で書いて先へ進む。答えが返ってきたら上書きする。
  評価は1対象1行の上書きで持つので、先に書いて後から直せる
- 取得できないものや判断に迷うものを**勝手に埋めない**。分からなかったことは分からなかったと
  書いて残す

**聞くきっかけ**（例示であって網羅ではない）:

- 情報源から取れなかった項目があるとき
- 数字と、蓄積されている評価が食い違うとき
- 過去の自分の評価と矛盾するとき（矛盾の検出自体は AI が強い領域）

### 人間の読みは、勝手に上書きしない

**人間が入れた意見や解釈を AI が塗り替えるときは、合意を取る。** これが唯一、先へ進む前に
人間を待つ場面。

**ただしこれも実行の承認ではない。** 聞くのは処理の可否ではなく、**見方を更新してよいか**。

- **聞き方**: 「上書きしますか」ではなく、
  **「前はこう見ていた。今回こう変わったと思う。これを最新の理解にしていいか」**
- 前の見方と新しい見方を並べ、**何がどう変わるのか・なぜ変わるのか**を示す。人間が判断できる
  材料を出す。材料の無い問いは、結局ただの承認になる
- 合意が取れるまで**その行は書き換えない**。ただし会話や他の作業まで止める必要はない
- 対象は `author` で判別する。**人間 / 対話** が書いた行が対象。**AI** が書いた行は AI が
  そのまま上書きしてよい

**守るのは書き換えの手前までで、疑ってはいけないという意味ではない**（2026-08-17 追加）。
人間が書いた見方は**現在合意している見方**であって、反証できない真実ではない。新しい材料が
それと食い違うなら、**黙って合わせにいかず、食い違いと理由を出して更新を提案する。**
出さずに合わせると、AI 側が先に折れるだけで学習が止まる。

理由は、評価が履歴を持たないため。1対象1行の上書きなので、**塗り潰した人間の読みは戻らない**
（[data-model.md](data-model.md#ナレッジの型)）。

**これは今の運用であって、完成形の姿ではない。** 「学習していると人間に意識させない」形と
「見方を更新してよいか毎回聞く」形は、そのままでは両立しない。**どう畳むかは未決**
（→ [未決の問い](#未決の問い)）。決まるまでは、この節のとおりに合意を取る。

## 実装との対応

**docs は「何を・なぜ」の正本、実装は「どうやるか」。** 同じことを二箇所に書かない。
docs を直したとき、どの実装を直すべきかはこの表から辿る。

### スキル

**分析する役は、予想（運用2）専用ではない。** 対話（運用1）からも振り返り（運用3）からも
必要な役を呼ぶ。複数の出走を総合する `horse-analyst` は、予想時には出走馬の全体を読み、
レース後には今回の出走評価で結論が変わる項目だけを読み直す。`entry-analyst` はどちらの場合も、
担当した1つの出走を越えて馬の性質を作らない。

### 分析する役（`agent/subagents/`）

**対象ごとに1つ。手順は各役の `instructions.md` が正本。** 分析する役の7つと検証する役は、
**8つとも中身が書いてある**（2026-08-16）。**枠だけの役はもう無い。**

**分析する役は、まず渡された調査資料と DB を読む**（2026-09-05 更新）。材料不足が判断に
効くときは、対象、必要な事実、その事実を使う判断をCodexへ返す。CodexからClaude Codeへ渡す
経路では、分析する役自身が外部サイトや動画を確認したり、事実データを登録したりしない
（→ [compliance.md](compliance.md)、[agent-design.md](agent-design.md)）。

**役の質は、書ける量ではなく、事実からどこまで読めるかで決まる**（2026-09-06 訂正）。
1つのレースと出走の評価には、その対象で起きた事実と、そこからの読みを書く。経験していない条件や
分からなかったことを、本文を慎重に見せるためだけに並べない。
**一方で、短い要約へ縮めない。** 対象の中で判断に効くラップ、位置の動き、相手との比較、負荷、
着差が生まれた区間、人間の観察を、そこからの読みと一緒に残す。**必要な情報を入れ切ることを
文字数より優先する。** 出走評価は700文字程度を、材料の取りこぼしを疑う最低限の見直し目安にする。
700文字へ達したことを完成条件や上限にはせず、特筆事項があれば必要な分だけ増やす。材料が乏しい
出走で、文字数を作るための推測や同じ意味の言い直しは足さない。
**血統分析も、材料不足の報告や一般的な注意事項を削った分だけ短くしない。** 父系・母系5〜6代、
近親、父の子、母父と配合について、確認した事実、比較、そこから読める適性を掘り下げ、材料が
そろう血統ではディープインパクトの参考例と同程度の情報量と深さを保つ。
判断の基準は [agent-design.md の分析をどこで止めるか](agent-design.md#分析をどこで止めるか2026-08-17-決定)が正本。
**役を増やして解決しない。** それぞれの役の中で言える範囲を決める。

馬の総合分析、血統分析、1つの出走の分析について、観点、構成、必要な深さ、書かない内容と、
固定したディープインパクトの参考例の使い方は
[analysis-quality.md](analysis-quality.md)を正本にする（2026-09-08 決定）。参考例から学ぶのは、
観点の広さ、根拠のつなぎ方、材料に応じた情報量であり、ディープインパクトについての結論や文章を
別の馬へ移さない。

**どの範囲の材料から言っているのかも一緒に返す。** DB に入っている出走は選ばれて入っているので、
そこから出した傾向は騎手・厩舎・コースの全体ではない（→
[見た範囲と偏りを返す](agent-design.md#見た範囲と偏りを返す2026-08-17-追加)）。**同じ事実を
2つの材料として数えない**という決まりもここに含まれる。その馬自身の実績は、産駒の傾向という形で
血統の側へ戻さない（→ [agent-design.md](agent-design.md#種牡馬の見立てを産駒ごとに書き直さない)）。

**血統をどう読むかは [agent-design.md](agent-design.md#血統をどう読むか2026-08-16-決定) が正本。**
材料の種類ごとに効き方の順序を付けること、**血統評価はその馬の血統だけで決まること**、反証できる形で書く
ことを決めてある。実績と血統を突き合わせるのは `horse-analyst` の担当。

**horse-analyst は `horse_notes` を自分で書かない。** 対話で作ると決めた評価なので、見立てを
返してオーケストレーターが書く（[data-model.md](data-model.md#ナレッジの型)）。

レース後の振り返りでも `horse-analyst` を使う。各出走の評価を確定して人間の観察と照合したあと、
12項目のうち結論が変わるものだけを更新候補として返す。変更対象外の項目を含む全文の書き直しには
せず、反映前に `verifier` が変更前との違いを確認する。詳しい順序と例外は
[analysis-quality.md](analysis-quality.md#レース振り返り後の更新)を正本にする。

| 役 | 見るもの | 評価の行き先 |
| --- | --- | --- |
| horse-analyst | 予想するレースの出走馬を総合して評価し、レース後は結論が変わる項目だけを更新する | `horse_notes` |
| pedigree-analyst | 血統から適性の素地を読む | `pedigree_notes` `progeny_notes` |
| jockey-analyst | 騎手の乗り方・仕掛けどころ | `jockey_notes` |
| trainer-analyst | 厩舎の仕上げ方・ローテ | `trainer_notes` |
| course-analyst | コースの傾向 | `course_notes` |
| entry-analyst | ある出走で何が起きたか | `entry_notes` |
| race-analyst | レースのレベル・展開・馬場 | `race_notes` |
| verifier | 分析の結果を蓄積と突き合わせる | 書かない。指摘を返す |

### 画面

**まず読むだけの画面を一通り作る**（2026-08-16 決定）。**評価は画面から直せるようにしない。**
画面から評価を直せると「人間が手で入力する」前提が画面側に固まってしまう
（→ [やらないこと](#やらないこと)）。

**例外は、まだ確かめていない材料の受け皿1つだけ**（2026-08-22 決定）。外で見かけた話を
その場でスマホから残せるようにする。**入るのは評価ではなく材料**で、
[`memos`](data-model.md#memos) に置かれたあと、読んで確かめたうえで宛先が決まる。
**画面から評価へ直接つながる経路は作らない**ので、上の決定の趣旨は変わらない。**入稿する側に
分類させない**のもここから来ている（分類を人間にやらせると、そこが手作業として固定される）。

**管理者だけが使うものは `/dashboard/` の下にまとめる。** 一般の画面と混ざらないようにする。

CodexがClaude Codeの実装・分析を確認して差し戻した内容と、Claude Codeから返った修正結果は、
改善のために一時的にローカルファイルへ残す。書き込みと管理はCodexが担い、Claude Codeには
記録の保存方法、往復数の集計、管理画面を実行上の責務として持たせない。Claude Codeへ渡すのは、
修正に必要な指摘と元のタスクMarkdownだけにする。

記録はDBへ入れず、`.claude/review-runs/<年月>/<実行記録のID>.json` に1依頼1ファイルで置く。
管理画面は保存済みのJSONをその都度読み、集計結果を別ファイルへ保存しない。過去の実行は正確な
往復内容が残っていないため復元せず、この仕組みを入れた後の実行だけを対象にする。自動削除と
画面からの削除は作らない。

ローカルファイルはVercelのデプロイ先から読めないため、記録の中身はローカルで起動した画面だけに
表示する。デプロイ先から確認する必要が出た時点でテーブルを作り、実行記録IDと往復番号を使って
ローカルのJSONを重複なく取り込む。今は将来のテーブルを作らない。

**URL は内容だけで決め、閲覧レベルは URL に出さない。** レベルは
[lib/access/](../lib/access/) の表1つで持つので、**公開範囲を変えても URL は変わらない**。
設計は [architecture.md のアクセス制御](architecture.md#アクセス制御)。

**レベルは動かす前提。** 馬・騎手・厩舎・コースを friend にしてあるのは今の判断で、
後から member へ降ろす可能性がある。

**だから評価の本文は、今のレベルではなく member が読む前提で書く**（2026-08-18 決定）。
馬の画面は `horse_notes` の本文をそのまま出しているので、**レベルを降ろした瞬間に本文がそのまま
読まれる。** 分析したときの取得状況や役の分担のような内部の作業情報を本文に入れず、
**公開範囲を変えても本文を書き直さなくていい状態**を保つ。決まりは
[agent-design.md](agent-design.md#評価の本文と返すだけのメモ2026-08-18-決定) が正本。

**評価の本文は Markdown として表示する。** 血統評価の既定の見出しは本文より大きい太字にし、
見出し名だけを独立した行に置いた既存の本文も同じ見た目にする。血統評価の見出しの書き方は
[agent-design.md の本文の型](agent-design.md#本文の型2026-08-16-決定)を正本にする。

**馬の詳細画面には `entry_notes` だけを出し、`race_notes` は出さない**（2026-09-09 決定）。
馬の詳細画面で読みたいのは、その馬が各レースでどうだったか。だから出走の履歴に並べるのは、
その出走について書いた `entry_notes` の本文だけにする。`race_notes` はレース全体について
書いたもので、同じレースに出た全頭で同じ本文になるうえ、その馬について書いた内容と読み違えられる。
`race_notes` を出すのはレースの詳細画面の「レースの振り返り」だけにする。

**一覧の画面には検索を付ける。** 馬名・騎手名・厩舎名・レース名を、部分一致で探せるように
する。

**馬の一覧はページ送りにする。** 1ページ50頭で、前へ・次へで動く。件数はそのページの頭数ではなく、
表示区分と検索語に当たる全頭を出す。**上限で切ると、名前順で後ろの馬が一覧から消えて辿り着けなく
なる**ため。検索語と表示区分は URL に残し、区分を切り替えたときと検索したときは1ページ目に戻る。

**技術情報の画面は静的。** DB から引かず、書いた内容をそのまま置く。**最終更新日を画面に
出す**ことで、情報が古いかどうかを読む人が判断できるようにする。

## 未決の問い

**このファイルには置かない。** 未決はすべて
[development.md の未決の問い](development.md#未決の問い)に集約する。

**未決は「これをどう作るか」の問いなので、置き場は1つでいい。** 以前は「Vatesteed を使う人に
関係するか」で product と development に振り分けていたが、**振り分けの判断そのものが毎回
迷いを生み、実際には片側に偏って溜まった**ので、分けるのをやめた（2026-08-15）。

このファイルが持つのは、**確定していること**だけ。未確定に当たったら、ここに書かずに
development.md へ1行足して止まる。
